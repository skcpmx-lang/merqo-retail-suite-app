## 2. Architecture as it exists today

```
Electron main (packages/app/electron/main.ts)
 ├─ owns SQLite (better-sqlite3, WAL) — single writer
 ├─ route table (electron/ipc.ts) → @sauda/core services → SQLite
 ├─ optional LAN host (core/src/net/rpc.ts) — HTTP + AES-256-GCM envelope
 │    └─ shared "shop token" (settings.lan_token) authenticates the *machine*
 └─ renderer bridge `sauda.call(method, args)` (preload.ts)

Terminal mode (same Electron app!)
 ├─ keeps its own local SQLite file (never used for business routes)
 ├─ forwards every non-local route to the host over /rpc
 └─ sessions live in the host's **in-memory** Map
```

Centralisation of *writes* is real: in terminal mode `invokeRoute` proxies to the host for
everything except `print.*, app.*, lan.*, display.*, meta.*, license.fingerprint`
(`electron/main.ts:36-43`, `:428-438`), and the host re-resolves the user from its own table
(`ipc.ts:2022-2046`). That is a sound starting point — but it is a *shared-secret remote shell*,
not a device-authorised client/server product.

## 3. Confirmed defects

### D-1 — The Main Server dies with the window · HIGH · CONFIRMED DEFECT
`electron/main.ts:440-443` (`window-all-closed` → `app.quit()`) and `:446-451` (`before-quit` →
`stopLanHost()`). The LAN host is an `http.Server` inside the Electron main process, so closing the
POS window stops every terminal. Requirement PART 07 explicitly forbids this.
*Proposed fix:* dedicated server runtime owned by a tray-resident main process, window close =
hide, explicit tray "Stop server" with client-connected warning.
*Verification:* automated test that starts the runtime, closes the window, and asserts the port is
still listening; manual check on Windows.

### D-2 — Host mode is never re-armed after a restart · HIGH · CONFIRMED DEFECT
`bootstrapTransport()` (`main.ts:90-104`) only *records* `transport.mode = 'host'`. The HTTP listener
is started exclusively by the renderer calling `lan.startHost` (`ipc.ts:2011`). After a reboot the
settings still say `lan_mode = 'host'` while nothing listens — terminals fail with "connection
refused" and the UI gives no explanation.
*Fix:* start the host during app bootstrap when configured; surface start failures in the UI.

### D-3 — Any holder of one shared token is a full client · CRITICAL · CONFIRMED LIMITATION (by design, now unacceptable)
`rpc.ts:232-237`: the only machine-level check is `timingSafeEquals(provided, opts.token)`. There is
no device identity, no per-device license, no approval, and no device registry — anyone who learns
the token (a QR photo, a screenshot of Settings, an old backup) can drive the whole store with any
valid user account, from any private-range address.
*Fix (v1.1.4):* device identity + per-device signed license + mandatory administrator approval +
revocable device credentials (see `V1.1.4_MULTI_PC_DESIGN.md`).

### D-4 — Sessions vanish on host restart; no session table · MEDIUM · CONFIRMED DEFECT
`rpc.ts:193-…` keeps `sessions` in a `Map`. Any host restart silently logs out every terminal
mid-transaction (`AUTH_REQUIRED`), and there is no record of who was connected.
*Fix:* `terminal_sessions` table with hashed tokens, TTL, device binding and revocation.

### D-5 — `max_devices` on the license is decorative · HIGH · CONFIRMED DEFECT
`LicensePayload.max_devices` exists (`domain/types.ts:665`), is issued (`licensing/issue.ts:67`) and
displayed (`electron/ipc.ts:1988`), but nothing enforces it: grep shows no comparison against the
number of connected terminals. A 1-device license supports N terminals today.
*Fix:* per-device licenses + capacity enforcement on the server, with an auditable refusal.

### D-6 — No discovery, no QR pairing, no saved servers, no diagnostics · HIGH · CONFIRMED LIMITATION
`pages/Settings.tsx:1044-1090` offers exactly two fields (URL + token) and three buttons. There is no
UDP/mDNS discovery, no QR, no connection history, no latency display, no error taxonomy
(isolation/firewall/wrong subnet). PART 09 is entirely unimplemented.

### D-7 — No push events; terminals show stale data · HIGH · CONFIRMED LIMITATION
The only push channel is `sauda:event` from main → renderer on the *same* machine (`preload.ts:12`).
Nothing tells a terminal that another terminal sold stock or voided an invoice; `POS.tsx` has no
`setInterval`, so product/stock tiles only refresh on navigation. Two terminals *can* oversell
perception (the host still refuses the second commit, so data stays correct — the UI just looks right
until the cashier hits save and gets an error).
*Fix:* event outbox + SSE/WebSocket stream + authoritative refresh on reconnect.

### D-8 — No idempotency keys anywhere · HIGH · CONFIRMED DEFECT
`grep -n "uuid\|idempot" services/sales.ts db/schema.ts` → **no matches**. A flaky Wi-Fi retry after a
timeout creates a second invoice. The existing POS has no client-side guard either.
*Fix:* `idempotency_keys` table + `Idempotency-Key` on writes, replayed responses returned verbatim.

### D-9 — No TLS on the LAN API · MEDIUM · CONFIRMED LIMITATION (documented)
`rpc.ts` uses `http.createServer` with an AES-256-GCM payload envelope keyed from the shared token.
Confidentiality is real; *server authentication* is not (any host with the token can impersonate the
Main PC), and there is no forward secrecy. PART 14 asks for HTTPS/TLS.
*Fix:* self-signed, pinned certificate per store, fingerprint shown in the pairing QR.

### D-10 — Backup has no schedule target, no verification drill, no migration workflow · MEDIUM
`services/backup.ts` has `createBackup` / `validateBackup` / `restoreBackup` / `pruneBackups` /
`shouldAutoBackup` — solid primitives. Missing: external/network destination, restore *wizard* with
pre-flight diff, and the Main-PC migration procedure of PART 20. `createBackup` uses the sqlite backup
API (safe), not a file copy.

### D-11 — Terminal installs a full standalone database · MEDIUM · CONFIRMED LIMITATION
Terminal mode still opens its own SQLite file and runs the setup wizard locally
(`main.ts:71-88` unconditional `bootstrapDatabase()`). Data directories diverge, the terminal can be
switched to `off` and used as an independent shop, and a burned terminal leaks a shop's local users.
*Fix:* explicit `installation_role` decided at setup; terminal role = no business DB, cached public
config only.
