# v1.1.4 · Phase 3 · Priority 1 — the three critical security gaps

Status: **implemented and automated-tested; Windows/DPAPI and two-PC behaviour NOT verified.**
Branch `arena/597b03e9-merqo-retail-suite-app`, PR #12 open, `main` untouched (`47576e1`, v1.1.3).

This document covers the three gaps the owner required closing before calling the network
architecture production-ready:

1. device private-key persistence (Windows DPAPI),
2. restart-safe replay protection,
3. authenticated certificate rotation and recovery.

Everything below was executed in this sandbox: Linux, real SQLite files, real TLS, real Ed25519
keys, real crash simulations (files moved by hand). **No Windows, no Electron runtime, no DPAPI, no
second PC** — those parts are stated as unverified and have manual procedures.

## 1. Device private-key persistence

### What was built

| File | Contents |
|---|---|
| `packages/core/src/net/device-keys.ts` | `Sealer` contract, `DeviceKeyStore` (sealed envelope), `createDeviceKeyRecord`, `loadOrCreateDeviceKey`, `DeviceKeyError` with six codes |
| `packages/app/electron/device-key-storage.ts` | DPAPI sealer via Electron `safeStorage`, `deviceKeyStore(profileDir)`, `canStoreDeviceKey()` |
| `packages/core/test/security-p1-v114.test.ts` | nine credential tests |

On-disk format: `SAUDA-DK1\n<sealer kind>\n<base64 sealed JSON>\n`, written to
`<profile>/device/device.key` with mode `0600` on POSIX, written to a temp file and renamed so a
crash cannot leave a half file. The sealed JSON holds the device id, store id, Ed25519 private key
(PKCS#8), matching public key (SPKI) and creation time.

### Binding to a security boundary

* On Windows the sealer is Electron `safeStorage`, which uses **DPAPI in the current user's scope** —
  the same boundary that already protects the shop database. A copied file does not open for another
  Windows user or on another machine.
* The `kind` field records the boundary (`dpapi-user`, or `safe-storage-<platform>`), and a blob whose
  kind differs from the running context is refused with `KEY_INACCESSIBLE` **before** any decryption
  attempt.
* **Machine-scope DPAPI is deliberately not supported:** on a shared shop PC it would let any local
  Windows user sign requests as that device. This is documented as an unsupported configuration, not
  a silent fallback.

### Failure policy (all tested)

| Situation | Result | Code |
|---|---|---|
| no credential, first enrolment (`allowCreate: true`) | generated once and stored | — |
| no credential on an approved device | refused; nothing generated | `KEY_MISSING` |
| file present but unreadable (permissions/IO) | refused | `KEY_INACCESSIBLE` |
| envelope header/JSON broken | refused, file left in place | `KEY_CORRUPT` |
| sealed for another user/machine (kind mismatch or failed unseal) | refused | `KEY_INACCESSIBLE` |
| credential belongs to another device id or store | refused | `KEY_DEVICE_MISMATCH` |
| existing credential about to be overwritten | refused unless `replace: true` | `KEY_ALREADY_EXISTS` |
| platform cannot encrypt (`isEncryptionAvailable() === false`) | refused, **no plaintext written** | `SEALER_UNAVAILABLE` |
| stored private key does not match the stored public key | refused | `KEY_CORRUPT` |

There is no code path that regenerates a credential for an already-approved device: a missing or
damaged credential always ends in re-pairing, which an administrator approves.

### Test evidence (9 tests, `security-p1-v114.test.ts`)

survives an application restart (new store instance, same sealed file) · plaintext PEM never appears
in the file (byte scan) · refuses to overwrite · missing credential is `KEY_MISSING` and nothing is
created · corrupt payload is refused and left on disk · another user/machine cannot open it ·
another device id or store is refused · no plaintext fallback when the sealer fails · tampered
keypair is refused.

Only a substitute AES-256-GCM sealer could run here. **DPAPI itself is NOT VERIFIED** (§4).

## 2. Restart-safe replay protection

### The gap

Milestone B used an in-memory `ReplayGuard`. A captured signed request stayed reusable after any
restart — and a restart is easy to provoke (tray restart, crash, power loss).

### What was built

* Schema v6 (additive, pre-migration backup as before) adds
  `device_nonces(device_id, nonce, seen_at, expires_at, PRIMARY KEY(device_id, nonce))`.
* `packages/core/src/net/replay-store.ts` — `SqliteReplayGuard`:
  `INSERT … ON CONFLICT (device_id, nonce) DO NOTHING`, then `changes === 1` means "first time".
  The statement is atomic inside SQLite, so concurrent duplicates cannot both win, and the decision
  survives process restart, machine reboot and crash.
* `packages/core/src/net/device-auth.ts` — `verifyRequest` now accepts any `NonceGuard` and, crucially,
  **verifies the signature before claiming the nonce**, so an attacker without the device key cannot
  burn a device's nonce space.
* The timestamp window (±120 s) is unchanged and still checked before the nonce claim.
* Expired rows are pruned lazily (default: at most once a minute), so the table stays tiny.

### Test evidence (7 tests, `replay-v114.test.ts`)

| Test | Proves |
|---|---|
| refuses a previously accepted request after a server restart | the exact gap: same nonce + same timestamp, new server process, same DB → `409 REPLAY` |
| accepts at most one of several concurrent identical requests | 6 parallel identical requests → exactly 1 × `200`, 5 × `REPLAY` |
| keeps nonces per device | the same nonce string from two devices is accepted for both (no cross-device interference) |
| does not let an unauthenticated request consume a nonce | forged signature → `BAD_SIGNATURE`, then the honest request with that nonce → `200` |
| rejects an expired timestamp without recording the nonce | `STALE_REQUEST`, then a fresh request with the same nonce → `200` |
| unit: remembers a nonce across guard instances | durability independent of the HTTP layer |
| unit: stores only nonce/timestamps | no request body or signature material in the table |

## 3. Authenticated certificate rotation and recovery

### The gap

Milestone B could generate, persist and `rotateServerIdentity()`, but rotation was a single
unauthorised function call with no journal: a crash between the two renames could leave no usable
identity, and nothing tied a rotation to an administrator decision.

### What was built (`packages/core/src/net/rotation.ts`)

1. **Authorisation first.** `authorizeRotation(db, { oldFingerprint, reason, adminUserId })` writes a
   `cert_rotations` row (schema v6) naming the fingerprint being replaced. `beginRotation()` refuses
   unless that row exists, is `pending`, and matches the certificate actually on disk.
2. **Prepare, then swap.** The new pair is written as `server.crt.next` / `server.key.next` (key
   first, mode `0600`) and a `rotation.json` journal records `prepared` with both fingerprints.
3. **Commit.** Old pair renamed to `*.old-<stamp>` (kept, never deleted), journal `swapped`, new pair
   renamed into place, journal removed, DB row `completed` with the new fingerprint.
4. **Recovery on boot.** `recoverRotation()` rolls forward (crash before/inside the swap, or after the
   swap before cleanup), or aborts and keeps the old identity when the new pair is missing/corrupt.
   It never generates an identity and never leaves a half-rotated state.
5. **Clients keep failing closed.** Pinned clients reject the new certificate (`CERT_MISMATCH`) and
   require an administrator-approved re-pairing. There is no "trust on rotation" path.

### Test evidence (9 rotation tests in `security-p1-v114.test.ts`)

unauthorised rotation refused (`ROTATION_UNAUTHORIZED`) · authorised rotation changes the pin, keeps
`*.old` backups, records the row as `completed` · a stale authorisation cannot be reused · crash
between prepare and swap → recovered to the new pin · crash in the middle of the swap (certificate
moved aside, key still there) → recovered · crash after the swap before cleanup → recovered · corrupt
new certificate → aborted, old identity still serving · pinned client rejects the rotated certificate
(`CERT_MISMATCH` with the actual fingerprint reported) · certificate replaced outside the rotation
process is refused (`IDENTITY_MISMATCH`/`IDENTITY_CORRUPT`).

### When recovery cannot be authenticated

If the new pair is corrupt and the old pair is gone, the machine has no identity it can prove. The
server refuses to start (`IDENTITY_MISSING`) rather than minting a new one. Recovery then requires an
administrator to authorise a fresh identity **and** to re-pair every client: the clients are pinned to
the old fingerprint, so they will not connect to a new one on their own. That is the intended
behaviour, not an inconvenience.

## 4. NOT VERIFIED (manual procedure required)

| Item | Why not verified | Manual check |
|---|---|---|
| DPAPI sealing and unsealing on Windows | no Windows/Electron in the sandbox | enrol a client on Windows, close the app, reopen: the device must still authenticate without re-pairing; then copy `device\device.key` to another Windows user account or PC and confirm `KEY_INACCESSIBLE` |
| Credential survives a Windows reboot | no reboot available | reboot, relaunch, confirm no re-pairing is required |
| Credential is unreadable as plaintext on disk | only the envelope is proven here | open `device.key` in a hex viewer on Windows: no `PRIVATE KEY`, no readable JSON |
| Machine-scope DPAPI explicitly unsupported | design decision, no Windows test | confirm the app never writes a machine-scope blob (single sealer, kind = `dpapi-user`) |
| Rotation on real hardware | no second PC | rotate on PC-A, confirm PC-B shows a pin-mismatch error and requires administrator re-pairing; confirm `*.old` files exist and the new pin is shown in the UI |
| Interrupted rotation on real power loss | simulated by moving files | cut power during rotation (or kill the process between steps), restart, confirm recovery message and a working identity |
| Replay protection across a real restart of the Electron app | simulated in-process | accept a request, restart the app from the tray, resend the captured request with `curl --insecure --cert`-style tooling: expect `409 REPLAY` |

## 6. Open risks

1. `device_nonces` grows with traffic until the prune runs (bounded to one prune per minute; rows
   expire after 240 s). A long-running shop keeps a few hundred rows.
2. Nonce pruning is lazy: a server that never receives a request keeps expired rows until the next
   request. Harmless, but not tidy.
3. The DPAPI sealer depends on Electron `safeStorage`; on a Windows machine where the user profile is
   on a network share, DPAPI behaviour is **not** verified and must be tested manually.
4. Rotation does not yet have a UI; `authorizeRotation`/`beginRotation`/`commitRotation` are core
   APIs. The administrator workflow lands with Milestone E (device administration screen).
