# MERQO v1.1.4 — Event → Screen Refresh Map

Status: implemented (Phase A item 5). Automated coverage: `packages/app/test/shop-events.test.ts`
(18 tests) plus the transport end-to-end test `packages/app/test/client-mode-e2e.test.ts`.

## 1. Rule that everything else follows from

The Main PC event stream is a **hint**, never a data source.

- An event says *"something of this kind changed"*; the screen then re-reads its data through
  the normal authenticated route (`/api/v1/rpc`), which runs on the Main PC and re-checks the
  user's permissions.
- Refreshers are called **with no arguments** — no event payload ever reaches the UI
  (enforced by test: `planForEvent`/`ShopQueryRegistry` carry no data and `register()` takes a
  zero-argument function).
- Therefore a withheld, duplicated, reordered or maliciously shaped event can only *delay* a
  refresh. It can never inject a value into the UI, and it can never authorise anything.

Fallbacks:

- an event type that is not in the table but starts with a known family (`sale.`, `stock.`, …)
  refreshes the union of that family — a new server-side event kind cannot silently stop the UI
  from updating before this file is touched;
- an **unknown** type, an empty type, a `resync` (truncated history, server restart) or a
  sequence gap refreshes **every mounted screen**;
- connection-state changes (`state: open/closed/error`) refresh nothing; the reconnect path
  re-subscribes from the last seen event id and the server replays or sends `resync`.

## 3. Which page registers which key

| Screen | Registered key(s) | Refresh function |
| --- | --- | --- |
| Dashboard | `dashboard` | `load()` |
| POS | `pos-catalog` | re-reads the catalogue **and** re-validates unsent cart lines |
| Products | `products` | `load()` |
| Sales | `sales` | `load()` |
| Stock (Stock Ops) | `stock` | `loadTab()` (current tab only) |
| Purchases | `purchases` | `load()` |
| Customers + Suppliers (Parties) | `customers`, `suppliers` | `load()` |
| Cash | `cash` | `load()` |
| Accounting | `accounting` | `load()` |
| Expenses | `expenses` | `load()` |
| Reports | `reports` | `run()` (current report only) |
| Devices / Licensing (Settings) | `devices`, `license` | panel `load()` |

`settings` is intentionally **not** registered by the settings form: reloading it under the
owner's cursor would discard half-typed, unsaved fields. Business settings changes are already
reflected after `settings.update` returns, and other screens refresh on `settings.updated`.

## 4. Coalescing, ordering and idleness

- **Coalescing:** events arriving within 150 ms produce at most **one** refresh per screen.
  Ten sales in a second cost one refetch, not ten.
- **Duplicates / out-of-order:** an event id that is not greater than the last applied id is
  dropped (`ignoredDuplicates`). A reconnect that replays a block is therefore harmless.
- **Unmounted screens are idle:** the refresher is unregistered on unmount, and the registry
  only schedules keys that have at least one live refresher.
- **Failure isolation:** a screen whose reload throws is reported to `onError` and does not
  stop other screens from refreshing.
- **No duplicate refreshes:** each key flushes at most once per burst even if three events
  named it.

## 5. POS: hints never re-price a cart

`pos-catalog` fires for sale/stock/price/product events. In the POS screen it does **not**
rewrite the cart. It only (a) reloads the catalogue for the search results, and (b) re-runs the
read-only `sales.validateCart` for lines already in the cart and marks the affected lines with
`• যাচাই করুন`. The price on screen changes only when the cashier presses **পরিবর্তন দেখুন**,
which applies the server's numbers to those lines. See
`docs/V1.1.4_REQUIREMENTS_MATRIX.md` and §6 of the same for the commit-time conflict contract.

## 6. Resync / unknown → full refresh

`ShopQueryRegistry.handle({ kind: 'resync', from })` schedules every registered key and bumps
`appliedFullRefreshes`; `planForEvent(undefined)` and `planForEvent('something.new')` do the
same through `full: true`. This is what keeps the UI correct when the server's outbox was
trimmed: the client gives up on incremental hints and simply re-reads the screens it has open.
