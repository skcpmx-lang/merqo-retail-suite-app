# v1.1.4 · Phase 3 · Milestone D — legacy retirement (partial, reported honestly)

**Status: the security-critical half is DONE and tested; the full renderer migration is NOT done.**
PR #12 stays open, `main` untouched. This file exists so the gap is documented rather than implied
away.

## 1. What is done

| Change | File | Evidence |
|---|---|---|
| `/api/v1` client: HTTPS-only, pinned, signed, session-aware, idempotency-key aware | `packages/core/src/net/v1-client.ts` | 9 tests (`v1-client-v114.test.ts`) |
| Legacy shop-token tunnel binds **loopback only** by default | `packages/app/electron/lan-policy.ts`, `packages/app/electron/server-runtime.ts`, `packages/core/src/net/rpc.ts` (`host` option, `bound_host`) | 6 tests (`lan-bind-v114.test.ts`, `app/test/lan-policy.test.ts`) |
| Explicit, documented, disabled-by-default compatibility switch | `SAUDA_ALLOW_LEGACY_RPC=lan` | policy tests; any other value is ignored |
| Health/log signal when the deprecated mode is on | `server-runtime.ts` logs a warning and reports `bound_host` | code path only — not exercised on Windows |

### What "retired from network access" means here

* The `/rpc` tunnel still exists **on the local machine** so the renderer's IPC path and printing keep
  working exactly as in v1.1.3. It is bound to `127.0.0.1`, so no other PC on the LAN can reach it.
* The only network-facing API is `/api/v1` over TLS, which requires a device Ed25519 signature, an
  approved device and a session bound to that device. A shop token alone grants nothing.
* A plaintext HTTP request to the `/api/v1` port never reaches a protected operation: the TLS
  handshake fails, and the legacy `/rpc` path returns 404 even when the request is correctly signed
  (both asserted in `v1-client-v114.test.ts`).

## 2. What is NOT done (and is not claimed)

1. **The renderer still talks to the local host over IPC**, not over `/api/v1`. IPC is a local,
   sender-validated bridge — it is not a network surface — but it is not the `/api/v1` DTO layer either.
2. **Terminal mode still uses the legacy token transport to reach a remote host.** It is now
   loopback-only, so this path cannot work across the LAN at all: a remote terminal must be migrated to
   the v1 client (device credential + login + SSE). That wiring needs the device-management UI from
   Milestone E and a real two-PC test to be trusted; it is **not** implemented in the app yet.
3. **No client-side session/credential flow in the UI**: there is no "pair this PC" screen yet.
4. **SSE is not consumed by the renderer** (the client exists and is tested in core).

Consequence, stated plainly: **between D and E the app is not usable as a multi-PC system.** Local
single-PC use (the v1.1.3 feature set, all local IPC) is unaffected, which is why nothing was removed
from the local path.

## 4. NOT VERIFIED

* Electron behaviour of the loopback-only listener on Windows (the binding is tested at the Node level).
* Windows Firewall prompts after the bind change.
* Any real two-PC connection attempt (no second PC here).

## 5. Manual check for the owner

1. Install v1.1.4 on PC-A, start the Main Server, and from PC-B run
   `curl -k -X POST https://PC-A:port/rpc` → must fail (`curl` cannot complete TLS to the plaintext
   port) and `curl -X POST http://PC-A:port/rpc` → must fail to connect (nothing is listening there).
2. On PC-A, confirm the renderer still prints, sells and reports (local IPC unchanged).
3. Set `SAUDA_ALLOW_LEGACY_RPC=lan`, restart: the app must log a deprecation warning and the old
   tunnel must become reachable — this proves the switch is explicit rather than a hidden default.
