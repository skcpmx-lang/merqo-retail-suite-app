# v1.1.4 Phase 3 — Client database isolation (finding D-11)

Status: implemented, guarded at runtime and covered by automated tests. Windows/two-PC
behaviour remains **NOT VERIFIED** (see `docs/V1.1.4_WINDOWS_TWO_PC_VERIFICATION.md`).

## 1. The problem

v1.1.3 opened the same shop database on every machine and relied on the renderer to send
business calls to the Main PC. Nothing in the database layer stopped a client from
writing locally. One missed route, one new screen, one retry after a timeout — and the
client would commit a sale into its own copy of the shop. That copy would then be shown
as current data, backed up as if it were the shop, and could later be restored over the
real shop.

## 2. What changed

| Layer | Control |
| --- | --- |
| Role detection | `detectDatabaseRole(file)` reads `settings.lan_mode` from a **read-only** connection before anything else happens. `terminal.json` (a saved server or a device key) also marks the install as a client. |
| Opening | `openClientDatabase({file})`: an **existing** file is opened with migrations disabled — no migration, no seed, no copy, no delete. A missing file gets a schema with **no reference data seeded**, so a client never invents products, categories or units. |
| Runtime | `guardClientDatabase(db)` wraps the handle. Only `settings`, `meta`, `schema_migrations` and a local `audit_logs` are readable/writable. Every other table raises `ClientIsolationError`. |
| Licence gate | Skipped locally in client mode (`ctx.mode === 'client'`): a client holds no authoritative licence, and the Main PC re-checks it on every request it serves. |
| Auto backup | Not scheduled in client mode: a client's file is not the shop. |
| Server runtime | Not started in client mode. |
| Route selection | `mode-policy.ts` decides local vs remote; business routes are forwarded over `/api/v1` (pinned TLS + device signature). |
| Mode change | `decideModeChange()` refuses to promote a paired client into a Main Server (`CLIENT_PROMOTION_BLOCKED`) and refuses client mode without a saved server (`NO_SERVER_CONFIGURED`). |

### Allowlist (the only tables a client can touch)

`settings` · `meta` · `schema_migrations` · `audit_logs` (local diagnostic log).

Everything else — sales, sale items, payments, products, stock movements, customers,
suppliers, purchases, journals, devices, outbox, idempotency keys — is unreachable
through the client handle, for **reads as well as writes**. A stale local copy therefore
cannot be presented as current shop data: the query throws instead of returning
yesterday's numbers.

## 3. Audit of database access paths in client mode

| Path | Runs on client | Database access | Verdict |
| --- | --- | --- | --- |
| `sale.*`, `payment.*`, `products.*`, `customers.*`, `inventory.*`, `reports.*`, `accounting.*`, `settings.get/update`, `backup.*`, `devices.*`, `auth.login` | **No — forwarded** to the Main PC | Host database only | Cannot touch the client file |
| `print.receiptHtml`, `print.print`, `print.document` | Yes | `getSettings(ctx.db)` (settings only) + `readVia(ctx, 'sales.get')` → forwarded | Sale data from host, layout from local settings |
| `app.info` | Yes | `meta`, `PRAGMA user_version` | allowed |
| `app.logs`, `app.openDataFolder` | Yes | none (files/logs) | allowed |
| `lan.status`, `lan.startHost`, `lan.stopHost`, `lan.modeOff`, `lan.regenerateToken` | Yes | `settings` | allowed; `lan.startHost` refuses while paired |
| `display.*` | Yes | none | allowed |
| `meta.permissions` | Yes | none (static list) | allowed |
| `license.fingerprint` | Yes | none (machine fingerprint) | allowed |
| `terminal.*` (connection, pairing, status) | Yes | `terminal.json` + sealed device key | allowed |
| `license.state`, `license.activateKey`, `license.activateFile` | **No — forwarded** in client mode | Host licence | A client's local licence never gates the UI |
| Startup: `integrityCheck`, `repairDatabase`, `install_id` | `install_id` only | `meta` | Integrity/repair skipped for a client |
| Auto backup scheduler | No | — | Not scheduled in client mode |
| Main Server runtime (listener, `/rpc`, `/api/v1`) | No | — | Not started in client mode |

## 4. Backup, restore and migration

| Concern | Main Server | Client |
| --- | --- | --- |
| Backups | Local, scheduled, `backup.create`/`restore` operate on the shop database | No local backup; `backup.*` is forwarded, so a client can ask the *host* for its backup |
| Restore | Allowed (permission-gated, audit-logged) | Local restore impossible: the guard blocks backup/serialize and every business write |
| Migration | Additive, with a pre-migration safety copy | **None.** An existing client file is opened with `skipMigrate`; its `user_version` is unchanged and no `.bak` file is created (asserted by a test) |
| Data deletion | Never without explicit operator action | **Never.** No migration, no re-seed, no cleanup writes to the client file |
| Existing customer data on a client install | — | Left byte-for-byte in place; simply not used. There is deliberately **no migration plan** for it, because it is never read |

Promoting a client install to Main Server therefore cannot silently re-use its old data:
the promotion is blocked while the device credential exists, and the operator must
disconnect the device first (then the file is a normal local database again).

## 5. Tests (`packages/core/test/client-isolation-v114.test.ts`, 12)

| Test | Proves |
| --- | --- |
| settings/meta read+write on a guarded handle | the client still has its own configuration |
| `createSale` on a guarded handle | a sale cannot be committed locally; row counts unchanged |
| `adjustStock`, customer insert, `DELETE FROM products` | stock/accounting/customer writes are blocked |
| `receiveCustomerPayment`, `createExpense`, `dashboardStats`, `runReport`, `createBackup` | payments, expenses, dashboards, reports and backups are blocked |
| `SELECT` over sales/products/customers/stock/journals | stale local business data cannot be shown |
| `exec('DROP TABLE …')`, `PRAGMA journal_mode = DELETE`, `db.backup()` | schema, pragma and backup escape hatches are closed |
| settings transaction vs sales transaction | legitimate settings writes still work |
| `onBlocked` callback | every attempted escape is observable for logging |
| `openClientDatabase` on an existing v1.1.3-style file | no migration, no seed, no `.bak`, identical row counts |
| `openClientDatabase` on a fresh file | schema only — zero products/customers/sales |
| SQL classifier | comments and string literals cannot spoof a table name |

Plus:
- `packages/app/test/mode-policy.test.ts` (10) — route selection (19 business routes
  forwarded, printer/display/LAN/app local, licence never local), mode-change rules,
  database-role descriptions.
- `packages/app/test/client-mode-e2e.test.ts` (1) — real TLS listener + real shop database:
  pair → pending refused → approve → login → sale through the transport lands on the Main
  PC (1 sale), the client file still has 0 sales, the guarded handle refuses reads and a
  direct `createSale`, and the product list comes from the host.

## 6. Residual risks

- The guard is enforced on the object the app passes around (`ctx.db`, `ctx.openDb`). Code
  that opened its own `better-sqlite3` handle on the same file would bypass it; no such
  call exists today (grep of `new Database(` shows only `db/connection.ts`).
- A client that is switched to `off` mode keeps the guarded handle until restart; the
  renderer is told a restart is required.
- Guarded statements are classified by parsing the SQL text. It is intentionally strict
  for writes (a single target table) and conservative for reads; a cleverly written query
  that hides a table behind a function call would be *blocked*, not allowed, because the
  guard fails closed when it cannot find an allowlisted table.
- Local `audit_logs` entries on a client are diagnostics, not the shop audit trail.
