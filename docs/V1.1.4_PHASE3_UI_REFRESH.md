# v1.1.4 Phase 3 — SSE-driven UI refresh

Status: implemented in the renderer and covered by renderer-level tests. Real-time
behaviour across two Windows PCs is **NOT VERIFIED**.

## 1. Principle

An event is a **hint**, never data. The renderer receives `{ kind, id, type }` and decides
*which mounted screens reload*. Each screen then refetches through the same route it
always used, executed on the Main PC under the normal permission table. Consequences:

- event payloads are never rendered, cached or used to compute a total;
- a withheld event (role visibility), a duplicate or a missed one can only delay a
  refresh — the next refresh, navigation or `resync` corrects it;
- there is still exactly one implementation of the business logic (on the Main PC).

Path: `EventStreamHub` → `V1Terminal.openEvents` → `TerminalManager` sink →
`webContents.send('sauda:v1-event')` → `preload.onV1Event` → `api.onV1Event` →
`shopQueries.handle(event)` → per-screen `load()`.

## 3. Duplicates, order and reconnect

| Situation | Behaviour |
| --- | --- |
| Same id delivered twice | ignored (`id <= lastId`), counted in `ignoredDuplicates` |
| Out-of-order / older id | ignored; `lastId` never moves backwards |
| Burst of events (10 sales in a second) | coalesced into one refresh per screen (150 ms debounce) |
| `kind: 'state'` (open/closed/error) | no refresh — a reconnect is followed by resume/replay |
| `kind: 'resync'` (history truncated, server restarted) | **full refresh** of every mounted screen, plus a boot/licence revalidation |
| Event for a screen that is not mounted | nothing queued (registration exists only while mounted) |
| A screen's `load()` throws | logged via `onError`, other screens still refresh |
| Client-side session revoked / device revoked | next refetch fails with the host's error and the app returns to login/pairing |

## 4. Screens wired

| Screen | Key | Hook |
| --- | --- | --- |
| Dashboard | `dashboard` | `useShopRefresh('dashboard', load)` |
| Products | `products` | `useShopRefresh('products', load)` |
| Sales | `sales` | `useShopRefresh('sales', load)` |
| Parties (customers + suppliers) | `customers`, `suppliers` | `useShopRefresh([...], load)` |
| POS | `pos-catalog` | `useShopRefresh('pos-catalog', …)` bumps a catalogue nonce; **the cart is never touched** |
| Reports | `reports` | `useShopRefresh('reports', run)` |
| Settings (devices) | `devices` | polled every 20 s (event wiring is a follow-up) |
| Stock, Purchases, Cash, Accounting, Expenses | — | not wired yet (refresh on navigation) |

## 5. Tests (`packages/app/test/shop-events.test.ts`, 15)

Mapping: sale/stock/price/customer/licence plans, unknown type → full, new action in a
known family. Registry: only affected screens refresh; bursts coalesce to one; duplicate
and out-of-order ids are ignored; `resync` refreshes everything once; connection-state
events do not refresh; unmounted screens stay idle; a throwing screen does not stop
others; unregistering stops refreshes; **a refresher is called with no arguments**, so a
payload can never reach the UI.

## 6. Residual risks

- Screens not listed in §4 still refresh only on navigation/focus.
- The POS catalogue refresh keeps prices correct, but a cart line already added keeps its
  captured price until the cashier re-adds it — deliberate (a changing price must not
  silently alter a draft), and the host revalidates on commit.
- Polled delivery (~1 s) means a refresh can lag by about a second on a busy LAN.
