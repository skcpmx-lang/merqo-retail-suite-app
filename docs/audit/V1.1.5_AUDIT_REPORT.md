# V1.1.5 — audit report

Living report. It records **what was actually read and proven**, module by module, and links every
finding to `V1.1.5_ISSUE_REGISTER.md`. Sections marked *(in progress)* are being filled as the audit
proceeds; a module is never marked audited because a test exists for it — only after its code was
read and its behaviour exercised.

## 0. Method

1. **Read the code**, not the test names. For each module: what it writes, what it assumes, what
   happens when a step fails.
2. **Prove the behaviour** with a test that fails on the old code, or record it as unproven.
3. **Classify** by what a shop experiences (S1 money/data loss → S4 hygiene).
4. **Fix at the root cause**, never by suppressing or loosening a gate.

Anti-goals, stated so they are not quietly violated: no assertion weakened to get green, no timeout
raised to hide a race, no `any` added, no blanket `eslint-disable`, no change that reduces what the
software refuses to do.

## 2. What the money path does right (verified, not assumed)

Worth stating explicitly, because it is the reason a shop can trust the numbers:

- **Integer arithmetic everywhere.** Money is an integer number of poisa, quantities are milli-units,
  costs are micro-poisa per base unit. `roundDiv` rounds half-up and is symmetric for negatives; it
  refuses zero and non-finite operands instead of returning `NaN`.
- **One write path for stock.** `applyMovement` is the only function that mutates
  `products.stock_base_milli`; sales, purchases, returns, adjustments and write-offs all go through
  it, so the movement ledger and the cached balance cannot drift *by construction* (their atomicity
  relative to *each other* was the A-01 gap, now closed).
- **Sale commit is transactional** (`sales.ts` wraps creation in `db.transaction`) and uses
  idempotency keys, so a double-clicked "Complete sale" cannot post twice.
- **Discounts are bounded server-side** — percent and minimum-price rules are enforced in the
  service, not in the renderer, so a client cannot bypass them by talking to the API directly.
  *(The floor's unit conversion was wrong — A-12 — but the enforcement itself was in the right
  layer, which is why the fix was local.)*
- **Negative stock is refused** unless the caller explicitly allows it, which only the
  correction/return paths do.

## 4. Main App: what was checked in the shell and IPC layer

- **Trust boundary.** Both preload bridges validate the sender; the audit step in `npm run verify`
  fails the build if either stops doing so. The window cannot navigate to remote content.
- **Authorisation.** IPC routes are registered with an explicit permission (`'any'` is deliberate for
  login/version only) and the wrapper enforces it before the handler runs. Permission strings are
  the same ones the RPC table uses, so the LAN path and the desktop path cannot disagree about who
  may do what.
- **Single writer.** The Main PC owns the SQLite file; clients talk only over the TLS API. The
  renderer never opens the database. *(Verified by reading the module boundary and the
  `db-boundary` test; re-checked in the client-mode E2E test.)*
- **No offline completed sale.** A Client PC has no local database (client-mode isolation test); the
  cart lives in renderer state only, so if the Main PC is down the sale cannot be completed — which
  is the intended, documented behaviour.

## 5. Known weaknesses the audit accepts for this release

1. **No accounting period lock (A-08).** A posting can be dated into an already-reported month.
2. **Two money formatters (A-09).** They agree today; the risk is future drift.
3. **Revocation is offline.** A revoked licence keeps working until expiry on an activated PC.
4. **Unsigned installers.** No Authenticode; SmartScreen will warn. Integrity comes from the
   published SHA-256.
5. **No interactive Windows/two-PC/hardware verification in this environment** — the VM gate stays
   BLOCKED and is reported as such (see `V1.1.5_VM_TEST_PLAN.md`).
