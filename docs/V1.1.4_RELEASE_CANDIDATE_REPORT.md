## 3. Windows build environment (reproducible procedure)

**Target:** Windows 10/11 x64. `better-sqlite3` is a native module, so the build host must be
Windows x64 — cross-compiling from Linux is refused by `@electron/rebuild`
(`node-gyp does not support cross-compiling native modules from source`), which is exactly what
happened here.

### 3.1 Build host requirements

| Requirement | Detail |
| --- | --- |
| OS | Windows 10 21H2+ or Windows 11, **x64** (not ARM, not WSL) |
| Node.js | 22 LTS x64 (`node -v` → `v22.x`) |
| npm | 10.x |
| Compiler | Visual Studio 2022 **Build Tools** with “Desktop development with C++” + Windows 10/11 SDK |
| Python | 3.12 x64 on `PATH` (node-gyp) |
| Git | any recent, with the branch checked out |
| Disk | ≥ 5 GB free (Electron win32-x64 + native rebuild + NSIS) |
| Network | npm registry; Electron/NSIS assets downloaded on first build |
| Signing | Optional code-signing certificate — see §7 |

Set once per machine:

```bat
npm config set msvs_version 2022
npm config set python "C:\Python312\python.exe"
```

has drifted.

## 7. Code-signing status — UNSIGNED (accepted by the owner)

- **Owner decision (2026-11-04): unsigned v1.1.4 installers are accepted.** Authenticode is no
  longer a release blocker; no certificate will be purchased. Signing gates were removed from the
  packaging scripts, the release workflow, `verify-installer.mjs` and the tests.
- No Windows code-signing certificate is available in this environment, so **nothing was signed**.
- The procedure in §3 produces an **unsigned** installer unless `CSC_LINK` / `CSC_KEY_PASSWORD`
  (or a hardware token) are provided by the build host.
- An unsigned build is **not** SmartScreen-trusted: Windows will show “Unknown publisher” and
  SmartScreen may require “More info → Run anyway”. That must be stated in the release notes if
  the owner chooses to ship unsigned.
- Signing status must be verified, not assumed:

```bat
powershell -NoProfile -Command "Get-AuthenticodeSignature 'Sauda-Retail-Suite-Setup-1.1.4.exe' | Format-List Status,SignerCertificate,TimeStamperCertificate"
```

`Status: NotSigned` is the expected result for an unsigned build; `Valid` with the vendor’s
subject is the only result that allows the phrase “signed” in any document.

## 10. Upgrade and rollback

### 10.1 Upgrade (v1.1.3 → v1.1.4)

1. Back up on the Main PC (Shop → Backup), copy the file off the machine, record row counts
   (products / sales / customers / dues) for the after-check in T03.
2. Close the app on every PC.
3. Install `Sauda-Retail-Suite-Setup-1.1.4.exe` on the Main PC; start it; Setup opens the existing
   database and runs `migrate()` (v5 multi-PC tables, v6 replay-protection tables — strictly
   additive; a pre-migration copy is written automatically).
4. Verify counts match the recorded numbers, then open a sale, a purchase and a report.
5. Install on each Client PC **and re-pair**: the v1.1.3 shared-token `/rpc` tunnel no longer
   exists, so a v1.1.3 client build cannot talk to a v1.1.4 Main PC.
6. Allow the Windows firewall prompt for **Private** networks only.

### 10.2 Rollback

1. Quit the app on all PCs (tray → Quit) so the database lock is released.
2. Uninstall v1.1.4 (the uninstaller preserves the data directory).
3. Reinstall the v1.1.3 installer.
4. Replace `%APPDATA%\Sauda Retail Suite\data\sauda.db` with the pre-upgrade backup and delete the
   `-wal` / `-shm` sidecars that belong to the v1.1.4 file.
5. Reinstall v1.1.3 on each client PC.

There is **no automatic schema downgrade**: v1.1.3 refuses a v6 database, which is why the backup
is mandatory, not optional.
