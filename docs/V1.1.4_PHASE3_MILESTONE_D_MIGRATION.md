# v1.1.4 Phase 3 — Milestone D: renderer & terminal migration to `/api/v1`

Status: **implemented and covered by automated tests; real Windows two-PC verification
still pending** (see §7). Branch `arena/597b03e9-merqo-retail-suite-app`, commit on top of
`b837c3a`. PR #12 stays open; nothing merged, no release.

## 1. What moved

The Client PC no longer has any remote path other than the authenticated `/api/v1`
transport. Concretely, in the Electron main process:

| Before (v1.1.3) | After (Milestone D) |
| --- | --- |
| `lanClient(hostUrl, token)` — shared shop token over HTTP `/rpc` | `V1Terminal` — pinned TLS, Ed25519 device signature, session bound to the device |
| Token stored in `settings.lan_token`, copied by hand | Device private key sealed per Windows user (DPAPI); **no shared secret stored** |
| Terminal trusted the host's word | Host validates signature, device status and session on every request |
| No event channel | Authenticated SSE stream, resumable, with `resync` on truncation |
| `lan.configureTerminal` accepted any `http(s)://` + 32-char token | Route now refuses with `LEGACY_TRANSPORT_REMOVED`; `terminal.configure` requires `https://`, a 64-hex fingerprint and the server certificate |

`main.ts` still routes everything through one place: the renderer calls
`sauda:invoke(method, args)` exactly as before, and in client mode `transport.client`
forwards the route to the Main PC. **No business logic was duplicated in the renderer** —
the local route table remains the only implementation, and the host rejects anything the
signed-in user's permissions do not allow.

## 3. Enrolment flow (as implemented)

1. The operator of the Main PC opens Settings → Network → *ডিভাইস* and creates a pairing
   code (`createPairingToken`, 2-minute TTL, single use).
2. On the Client, Settings → Network → *ক্লায়েন্ট কম্পিউটার সংযোগ*: address, SHA-256
   fingerprint and server certificate are saved; a device key pair is generated and the
   sealed key written **before** the claim is sent.
3. `POST /api/v1/pairing/claim` consumes the code and enrols the device as **pending**.
   The licence is checked here (store match, capacity) and a refused claim deletes the
   local credential again.
4. Only `approveDevice` on the Main PC moves the device to approved. **A valid licence
   never bypasses that step** — asserted by a test that pairs with a correct licence and
   still cannot log in.
5. After approval the normal login screen works unchanged: `auth.login` goes over
   `/api/v1` and the host returns the user with its permission list.
6. Revocation, rejection and pending are reflected in `terminal.status` and the panel;
   a revoked device gets `DEVICE_REVOKED` on every route and no route is executed.

## 4. Offline behaviour

- `invoke()` on a disconnected Client throws `OfflineError` (`code: 'OFFLINE'`). Nothing
  is written locally and nothing is queued: the Client keeps no business database of its
  own in client mode.
- A sale in progress stays in the renderer as an uncommitted draft. On reconnect the
  cashier must re-run the same flow, and the normal route handlers revalidate product,
  price, stock, session and licence state on the host before committing.
- Every write (`sale.*`, `payment.*`, `inventory.*`, `stock.*`, `accounting.*`, …) carries
  an idempotency key; the host's replay store returns the first result for a repeated key,
  so a retry after a dropped connection cannot create a second sale or payment.
- Tests: offline write commits nothing (host invocation count and `sales` table unchanged),
  repeated key executes once, a different key executes twice.

## 5. Event stream in the renderer

- `V1Terminal.openEvents` → `TerminalManager` sink → `webContents.send('sauda:v1-event')`
  → `preload.onV1Event` → `api.onV1Event` → `sauda:shop-event` window event.
- Last delivered id is persisted in `terminal.json`; a duplicate id after a resume is
  dropped, and `resync` re-runs the boot check (licence/session revalidation).
- Events are treated as hints only: pages refetch through the same routes they already
  use, so a withheld or missed event cannot corrupt on-screen state.

## 6. Operational limits closed / still open

Closed in this pass:

- **Per-device reconnect budget** (`sseMaxOpensPerMinute`, default 30/minute) → `429
  STREAM_RATE_LIMITED`, tested including per-device isolation.
- **Role-based event visibility**: `event-visibility.ts` maps licences, accounting,
  valuation and device presence to `settings.manage`/`report.view`; the sequence advances
  but the payload is withheld. Tested with a cashier session (no `accounting.` or
  `license.` payload reaches it) and a manager session (full visibility).
- **Scheduled retention**: `startEventRetention` runs at startup and hourly; refuses to
  run inside a caller transaction, uses `busy_timeout`, logs and continues after a failed
  tick. Policy in `docs/V1.1.4_PHASE3_RETENTION.md`.

Still open (honest):

- The stream is still polled (1 s) rather than pushed from the outbox writer.
- No push notification to a waiting client: an operator still has to press *অবস্থা দেখুন*
  (or wait for the 20 s poll) to see approval.
- Per-page refresh on `sauda:shop-event` is wired for boot/licence revalidation only; list
  pages still refresh on navigation/focus.
- Retention scheduler is started by the app, not by a Windows service; a Main PC that is
  never opened never prunes.
