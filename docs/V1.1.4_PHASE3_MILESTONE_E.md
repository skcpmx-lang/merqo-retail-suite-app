## 2. Behaviour

* **Explicit approval only.** A new device lands in `pending`; nothing in the app auto-approves.
  Approval and rejection require a signed-in user with `settings.manage`, and the handler refuses to
  act without an authenticated actor.
* **Capacity is enforced by the service.** `capacitySummary` reads the licence, a pending request
  cannot even be queued when all slots are used, and `approveDevice` re-checks before approving
  (so legacy rows or imports cannot bypass it either). Errors are explicit (`CAPACITY_REACHED`,
  `NO_LICENSE`, `DEVICE_REVOKED`).
* **Identity and last seen are visible** — device id, role, status, last-seen timestamp, plus the
  store id and the short certificate pin (e.g. `F961-1240-78DF-BF6F`).
* **Revocation invalidates credentials and sessions** (service-level: sessions are rejected from the
  next call; SSE streams are closed by the v1 host via `closeStreams(deviceId)`).
* **Pairing QR lifecycle:** a code is created on demand, is single-use, expires (10 minutes by
  default from the UI) and the QR payload contains only `{v, host, code, fingerprint}` — never a shop
  token or a password.
* **Re-pairing after credential loss** is the same flow: the device is revoked (or stays pending),
  the administrator issues a new code, the device pairs again and must be approved again.

## 3. Test evidence (6 tests, real database)

no signed-in user → every decision refuses · listing + capacity (licensed/approved) · a pending
request is refused once slots are full, and approval of an existing pending row still fails with
`CAPACITY_REACHED` · revoking invalidates the device's live session (`validateDeviceSession` throws) ·
rejected device never appears in the approved list · pairing code has a future expiry and a QR payload
whose keys are exactly `code, fingerprint, host, v` with no token or password.

`npm run verify` also runs `audit-ui`, which now reports **36 renderer files · 258 IPC routes · 195
call sites · wiring is consistent**, so every route the UI calls exists and every screen compiles.

## 5. Remaining gaps (stated, not hidden)

1. The panel lives in the existing **Settings → Network** section; there is no dedicated Devices page.
2. Approval does not yet push a notification to the waiting client; the client polls `devices/self`.
3. `devices.pending` and `devices.rename` exist as routes but the current panel derives pending
   devices from `devices.list` and does not expose renaming yet.
4. Milestone D's renderer migration is still open, so the panel's actions run over local IPC, not
   `/api/v1`. The pairing UI can create codes before the client side can consume them.
