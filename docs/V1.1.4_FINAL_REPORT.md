## C. Main App ↔ License Generator compatibility (verified)

New suite `packages/core/test/licensing-lifecycle-v114.test.ts` — **11 tests, all PASS**, driving the
generator's real `buildPayload` / `issueLicense` / `licenseFileText` against the app's real
`parseLicenseFile` / `verifyLicense` / `activate` / `getActivationState`, with ephemeral Ed25519
keypairs (no production key material):

1. generator `.sauda-license` file → activation succeeds;
2. activation survives an app restart (database file reopened);
3. per-PC licences for one store; store / device / role mismatches rejected;
4. licence minted for other hardware is refused and audited (no activation row written);
5. hardware replacement recovered by re-issuing for the same PC identity;
6. renewal replaces the previous activation;
7. tampered signed payload → `signature_invalid`; cosmetic JSON edit cannot change the activated org;
8. foreign signing key → `signature_invalid`;
9. empty / non-JSON / structurally wrong files never activate;
10. legacy v1 licences (no `store_id` / `device_id`) still verify → upgrade path intact;
11. activation-screen summary renders Bangla labels and expiry.

### Remaining blocker (single)

A Windows 10/11 **x64** host, or Actions write access to dispatch `release.yml`. Both routes build
unsigned installers with no certificate. Then: `verify-installer.mjs --dir artifacts` → fill
`<bytes>`/`<sha256>` in the release notes → `check-release-notes.mjs --require-filled` → draft
release → re-download and compare hashes → publish.

Pushing a `v1.1.4` tag also triggers the Windows build (artefact `sauda-windows-installers`); the
workflow is read-only and cannot publish by itself.
