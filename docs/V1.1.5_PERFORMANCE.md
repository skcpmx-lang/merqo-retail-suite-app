# V1.1.5 — performance work, measured

Every number below was produced on this machine by the script in §2, against a throw-away database.
No figure is estimated, and none is extrapolated to hardware that was not measured. Where a change
made something *slower*, it says so.

## 1. What was slow, and why

Every list screen and most reports filtered like this:

```sql
WHERE date(sale_date) BETWEEN date(?) AND date(?)
```

Wrapping the **column** in `date()` makes the index on `sale_date` unusable: SQLite has to evaluate
the function for every row, so each of these queries scanned the whole table. `scripts/bench.mjs`
reported it plainly, before any change:

```
query plans:
  sales by date: SCAN sales
```

On a 300,000-sale database (a few years for a busy shop) that is **27 ms per page of the sales list**
and **67 ms per daily report** — on a desktop PC with a spinning disk, several times that.

## 2. Method

- Database: throw-away file in the OS temp folder, `initializeApp` + one product, then *N* sales rows
  inserted with a direct `INSERT` (the service path costs 2–3 ms per sale, which is irrelevant to a
  read benchmark and would take an hour to seed).
- Queries: the real shapes — a one-month filtered, paged sales list, and the one-month daily report
  aggregate.
- 15 repetitions each, median reported; `EXPLAIN QUERY PLAN` recorded next to each figure.
- Machine: Intel Xeon @ 2.60 GHz, 4 GB RAM, Linux container, Node 22, SQLite as bundled with
  better-sqlite3 13.

## 3. Results

### 300,000 sales (65 MB database)

| Query | v1.1.4 | v1.1.5 | Change |
| --- | --- | --- | --- |
| Sales list, one month, page 1 | 27.4 ms (`SCAN sales`) | **0.03 ms** (`SEARCH sales USING INDEX idx_sales_date`) | ~900× faster |
| Daily report, one month | 66.9 ms (`SCAN sales`) | **26.9 ms** (`SEARCH sales USING INDEX idx_sales_day`) | 2.5× faster |

### 100,000 sales

| Query | v1.1.4 | v1.1.5 |
| --- | --- | --- |
| Sales list, one month | 10.6 ms | 0.03 ms |
| Daily report, one month | 20.5 ms | 4.8 ms |

### 3,000 sales (a small shop)

Both versions are under a millisecond; nothing here is worth a claim either way.

## 4. What was changed

1. **Sargable date ranges in the list queries** (`sales`, `purchases`, `payments`, `expenses`,
   `returns`, `cash sessions`, `attendance`): the column is compared against
   `YYYY-MM-DD 00:00:00` and `YYYY-MM-DD 23:59:59` through the new `dayStart`/`dayEnd` helpers in
   `domain/datetime.ts`. That is the same range for the timestamps the app writes, and it lets the
   existing `idx_sales_date` do the filtering *and* the ordering — no temporary sort.
2. **Migration 7 — expression indexes** for the aggregate/report queries that must keep using
   `date(column)` (`sales`, `purchases`, `payments`, `expenses`, `returns`, `cash_sessions`,
   `attendance`, `journal_entries`). Additive: no table, column or row changes; `user_version` 6 → 7;
   a `.pre-migration-v6-to-v7-*.bak` copy is written first, and the whole migration is one
   transaction.

The combination is why both rows above are fast: the list is indexed on the column, the reports on the
expression.

## 5. What was rejected, and why

| Idea | Why not |
| --- | --- |
| Only the expression index (no query change) | Measured at 300k rows: the list got **slower** (36.6 ms vs 29.1 ms) because the expression index cannot satisfy `ORDER BY sale_date DESC` and SQLite built a temporary B-tree. Shipping that alone would have been a regression on the most-used screen. |
| Only the query change (no expression index) | Reports still scan: 66.9 ms at 300k rows. |
| Rewriting the report SQL to also be sargable | The reports group by `date(column)`; splitting the filter from the grouping in a dozen reviewed queries is churn with no measurable gain over the expression index, in a patch release. |
| Caching report results | A shop needs today's numbers to be current; a cache here trades correctness for speed. |
| VACUUM / `PRAGMA optimize` on open | Startup cost for the whole database to speed one query; not justified by the numbers. |

## 6. Where the time goes now (unchanged, measured)

From `scripts/bench.mjs` at 400 products / 800 sales, which is why startup and write paths were left
alone this release:

```
startup (open+migrate+seed)   189.9 ms
createSale median              2.78 ms   p95 4.44 ms
products.list(page 1, 50)      1.5 ms
backup.create (VACUUM INTO)   50.8 ms
```

`createSale` is dominated by the work a sale actually does — stock movement, ledger postings, audit,
payments, cash session — not by a missing index. Nothing in that path was made faster by pretending.

**Re-measured after the v1.1.5 atomicity work (A-21 … A-27).** The same harness, after 43 service
functions were wrapped in `db.transaction(...)` and the sale path gained its coupon re-check, on the
same container:

```
createSale × 200 (all products pre-stocked)   434.0 ms
createSale median=1.99 ms p95=3.33 ms max=4.90 ms
backup.create (VACUUM INTO)                    65.0 ms
integrity=ok fk_rows=0   (products=1000 sales=2200 sale_items=2200)
```

Read that as "no measurable cost", not as a speed-up: the medians move with the machine, and the
atomicity changes are savepoints inside work the sale already did.

## 7. Reproduce

```bash
node scripts/bench.mjs --products 400 --sales 800      # planning + hot paths
```

The 300k-row figures come from the same query shapes seeded with a direct `INSERT` loop; the script
that produced them is described in §2 and the plans are reproduced by the tests in
`packages/core/test/migration-v7.test.ts` (`EXPLAIN QUERY PLAN` assertions), so a future change that
loses the index fails the suite rather than silently slowing down.
