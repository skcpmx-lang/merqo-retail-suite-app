# MERQO v1.1.4 — Security Re-Review (Phase A, item 7)

Scope: the Server/Client model shipped in v1.1.4 on top of v1.1.3 — `/api/v1` HTTPS transport,
Ed25519 device identity, device-bound sessions, authenticated SSE, the Main PC / Client PC split,
the licensing path, and the Electron trust boundary.

Method: read every control at its enforcement point, then confirm a **negative** test exists that
tries to break it. Where a control had no negative test, one was added (marked ➕). Where a test
found a real gap, the code was fixed (marked 🔧).

Status of this document: automated review only. Physical/Windows items are **NOT VERIFIED** and
are listed in §9 — they can only be closed by `docs/V1.1.4_WINDOWS_TWO_PC_VERIFICATION.md`.

## 1. Transport

| Control | Enforced in | Negative test |
| --- | --- | --- |
| TLS-only; no silent downgrade to HTTP | `v1-client.ts` (`https:` required), `api.ts` (`startLanApi` refuses without TLS material in production mode) | `v1-client-v114` "refuses a plaintext base URL instead of downgrading"; `api-v114` "refuses to start without TLS material"; `api-v114` "answers no plaintext HTTP request on the v1 port and never invokes a route" |
| Pinning by certificate fingerprint | `v1-client.ts` `checkServerIdentity` compares SHA-256 of the DER body | `tls-v114` "rejects a client that pins a different certificate", "fails closed on an empty or garbage pin", "derives the pin from the DER body, not the PEM text" |
| Certificate + pin rotation, authenticated and crash-safe | `security/cert-rotation` in core, admin authorisation row required | `security-p1-v114` (9 rotation tests) incl. "refuses to rotate without an administrator authorisation row", "refuses a certificate that was swapped outside the rotation process", "makes a pinned client reject the new certificate until an administrator re-pairs it" |
| LAN binding only, never a public interface | `net/api.ts` binds `0.0.0.0` with an address allowlist callback; `lan-policy.ts` decides | `lan-bind-v114`, `lan-policy` |

## 2. Device identity and requests

| Control | Enforced in | Negative test |
| --- | --- | --- |
| Ed25519 signature over method + device + body digest | `net/api.ts` `verifyRequest`, `net/v1-client.ts` `signRequest` | `api-v114` "rejects a missing signature", "rejects a tampered body (signature covers the body digest)", "rejects a device whose signing key does not match the registered key" |
| Replay protection (nonce + timestamp), durable across restart | `SqliteReplayGuard` | `replay-v114` (7 tests) incl. "refuses a previously accepted request after a server restart", "accepts at most one of several concurrent identical requests", "stores only a fingerprint of the request, never the body" |
| Device-bound sessions; session cannot move to another device | `net/api.ts` `SESSION_DEVICE_MISMATCH` | `api-v114` "rejects a session minted for a different device" |
| Revocation is immediate (sessions + open streams) | `revokeDevice` → `revokeDeviceSession` + `hub.closeDevice` | `devices-v114` "kills sessions the moment the device is revoked"; `sse-hardening-v114` "closes an active stream when the session is revoked mid-stream" |
| Pending devices get nothing but their own status | `net/api.ts` `DEVICE_PENDING` | `devices-v114` "keeps a new client pending — a valid licence alone never grants access"; `api-v114` "rejects a pending device but lets it read its own status"; end-to-end in `client-mode-e2e` |
| Admin approval, single-use pairing tokens, expiry | `pairingClaim` + `consumePairingToken` | `devices-v114` "accepts a code once and rejects a replay", "rejects an expired code"; `api-v114` pairing-expiry 410 path |
| Capacity from the Main PC licence | `enrolDevice` / `capacitySummary` | `devices-v114` "enforces the capacity stated on the Main PC licence", "keeps devices valid when capacity grows and refuses to silently drop them when it shrinks" |
| Store isolation at enrolment | `devices.ts` `STORE_MISMATCH` | ➕ `security-review-v114` "refuses a licence minted for another shop"; ➕ "keeps the store identity stable so a re-pair cannot silently rebind it"; ➕ "treats a device whose stored store no longer matches as revoked" (spliced/restored DB) |
| Role binding (a client POS cannot enrol as SERVER_POS) | `enrolDevice` role check | ➕ `security-review-v114` bad-role rejection (covered by the same suite) |
| Server-side authorisation on every route | `ipc.ts` route table permissions, independent of the renderer | `api-v114` "refuses a route the user has no permission for" (403 `FORBIDDEN`); `security-audit` cashier role checks |
| Idempotency for every write | `withIdempotency`, keyed by method + device + body | `devices-v114` "runs an operation once and replays the stored answer", "refuses a reused key with a different body"; `v1-client-v114` "replays the stored answer for a repeated idempotency key" |

## 3. Event stream (SSE)

| Control | Enforced in | Negative test |
| --- | --- | --- |
| Stream requires a device signature **and** a live session | `net/api.ts` stream route | `sse-hardening-v114` "refuses a session that has already expired", "refuses a revoked session" |
| Sessions expire mid-stream and close the stream | heartbeat re-authorisation | `sse-hardening-v114` "closes an active stream when the session expires mid-stream" |
| Sequence recovery: resume, gap detection, truncation | `net/sse.ts` + outbox floor | `sse-hardening-v114` "rejects a malformed Last-Event-ID instead of guessing", "treats a resume point beyond the newest event as wait for new events", "declares truncated history and resumes from the retained floor", "never sends the same sequence twice on one stream" |
| Bounded resources: stream count per device, slow-consumer drop | `EventHub` | `sse-hardening-v114` "enforces the concurrent stream policy", "replaces the previous stream when the same device reconnects", "drops the registration when a client disconnects", "closes a client that cannot keep up instead of buffering without bound" |
| Retention keeps the newest events and records the floor | `outbox` retention | `sse-hardening-v114` "never removes the newest events and records the floor", "keeps recent events even when the cap would allow removing them"; `sse-visibility-retention-v114` |
| Events carry no per-store leakage | `sse.ts` store filter | `sse-visibility-retention-v114` |
| Events are hints only (never a data source) | `shop-events.ts` calls refreshers with no arguments | `shop-events` "refreshers are called with no arguments"; design note in `V1.1.4_EVENT_REFRESH_MAP.md` |

## 8. Electron / IPC trust boundary

Guarded by ➕ `packages/app/test/electron-hardening.test.ts` (9 tests), which asserts the actual
source of `electron/main.ts`, `electron/preload.ts` and `index.html`:

- both `BrowserWindow`s set `contextIsolation: true`, `nodeIntegration: false`,
  `nodeIntegrationInWorker: false`, `sandbox: true`, `webSecurity: true`,
  `allowRunningInsecureContent: false`;
- no `webviewTag: true`, no `enableRemoteModule`, no `sandbox: false`, no
  `contextIsolation: false`, no `webSecurity: false` anywhere;
- `setWindowOpenHandler` always returns `action: 'deny'`; external links go to the system browser
  only for allow-listed **https** hosts; `will-navigate` and `will-attach-webview` are blocked for
  anything that is not our renderer;
- `ipcMain.handle('sauda:invoke')` calls `isTrustedSender(event)` **before** any dispatch and
  answers `UNTRUSTED_SENDER`; empty method names and non-array argument lists are normalised;
- the preload exposes a narrow `sauda` bridge via `contextBridge` and never `ipcRenderer` itself;
  no renderer source file imports `electron`;
- the renderer ships `default-src 'self'`, `script-src 'self'`, no `'unsafe-eval'`;
- no private key material in renderer or Electron sources.

The route table is also audited mechanically on every `npm run verify` ("IPC route + call-site
audit": 268 routes, 203 call sites, every `call()` name resolves to a route).

## 9. NOT VERIFIED here (requires Windows / two PCs)

These cannot be closed by Vitest and are **not** claimed as passed:

1. Windows 10/11 x64 behaviour of `safeStorage`/DPAPI sealing, including roaming-profile and
   OS-upgrade cases.
2. Firewall prompts, Windows Defender network-profile behaviour, and real Wi-Fi/LAN loss for the
   reconnect and offline paths.
3. Packaged-installer code signing, SmartScreen, and the absence of private keys in the built
   `.exe`/`app.asar` (only the source tree is scanned here).
4. Long-lived SSE streams (hours), real revocation latency over a real network, and behaviour
   across a Main PC restart while clients are streaming.
5. Physical device approval on the Main PC, QR/pairing flow with a real second PC, and printer,
   cash drawer, barcode scanner and customer display behaviour.
6. Upgrade from a real v1.1.3 installation.

See `docs/V1.1.4_WINDOWS_TWO_PC_VERIFICATION.md` — those rows stay **BLOCKED** or
**NOT VERIFIED** until an operator records real evidence.
