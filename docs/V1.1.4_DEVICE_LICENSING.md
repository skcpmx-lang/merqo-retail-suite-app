# Device licensing (v1.1.4)

How a licence file becomes *N approved PCs*, and what happens when one of them has to be taken away.
This is the authoritative description of device-count licensing as shipped in v1.1.4; the licence
format itself is in `04-licensing.md`, the LAN transport in `17-LAN-ARCHITECTURE.md`.

Everything here is **offline**. The Main App never contacts a MERQO server. A licence is a signed
file; a device is a row in the shop's own database. Neither can be changed without the right key or
the right person.

---

## 1. The two numbers that matter

| Number | Where it lives | Who can change it | Effect |
| --- | --- | --- | --- |
| **Licensed device capacity** | inside the signed licence payload (`capacity`) | only MERQO, by re-issuing the licence | hard ceiling on approved devices |
| **Approved devices** | `terminals` rows with `status = 'approved'` in the Main PC database | the shop administrator, on the Main PC | each approved device holds one seat |

The capacity is covered by the Ed25519 signature, so it cannot be raised by editing a file, a
database row, or a settings screen. A shop that needs a fourth till asks for a licence with
`capacity = 4`; the old licence keeps working until it is replaced.

## 2. Lifecycle of a device

```
            pairing code / QR
  (new PC) ───────────────────►  pending  ──── approve ────►  approved  ──── revoke ────►  revoked
                                   │                            │                          │
                            no data access               one licence seat           session ended,
                            no login                     per device                 no reconnect
```

1. **Pending.** A PC that asks to join is recorded as `pending` and can do nothing: no login, no
   read, no sale. This is deliberate — an unapproved machine must not be able to observe the shop.
2. **Approved.** An administrator approves it on the Main PC (Settings → Devices). Approval is
   refused once the number of approved devices equals the licensed capacity; the message names the
   limit, and **no seat is consumed** by a refused approval.
3. **Revoked.** The session is invalidated immediately and the live event stream is closed. A revoked
   device cannot log in again, and it stops trying: a revoked/expired/unapproved rejection is
   terminal and does not retry (`packages/core/src/net/sse-client.ts`).

Rejecting a pending request is free: it never occupies a seat, so a mistyped pairing code cannot
lock a shop out of its own capacity.

## 3. What binds a device

- **Ed25519 device identity.** Each PC generates a key pair on first run; the private key is stored
  with OS protection (DPAPI on Windows) and never leaves the machine. The Main PC keeps the public
  key, so requests are authenticated per device rather than per shop.
- **Session bound to the device.** A session token is issued to that device's key, is single-use for
  pairing, expires, and is refused if presented by another device.
- **Replay protection that survives a restart** (monotonic counters stored with the device key), so
  a captured request cannot be replayed after the Main PC reboots.
- **Hardware fingerprint** (licence level). The licence itself is bound to four weighted hardware
  components; replacing one component is tolerated, replacing the machine is not. This is separate
  from device identity and is described in `04-licensing.md`.

## 4. Revocation is offline — read this before selling a licence

Revoking a device in the Main App (or a licence in the License Generator) is a **local** action:

- in the Main App, revocation immediately ends the device session and closes its connection — the
  device cannot reconnect, because the Main PC is the authority it talks to;
- in the License Generator, revoking a licence stops it being exported again and marks the record,
  but a PC that was already activated keeps working until the licence's expiry date, because the
  Main App does not phone home.

There is no online kill switch. When a licence must stop working on a particular day, the tools are:

1. the **expiry date** (shorten it for the next issue),
2. **re-issue** with a new licence id and revoke the old one,
3. for a device that is physically present or reachable: revoke it in the Main App, which takes
   effect immediately.

This limitation is stated in the release notes and in `09-known-limits.md`. It is not a defect and
not covered up.

## 5. Limits that are enforced, not implied

| Rule | Enforced in | Test |
| --- | --- | --- |
| Capacity is read from the signed licence, never from the database | `packages/core/src/licensing/*` | `capacity-v114.test.ts` |
| A hostile/corrupt capacity row cannot raise the limit | capacity fallback path | `capacity-v114.test.ts` |
| Approval is refused at capacity, and a refused approval consumes nothing | device administration | `device-admin.test.ts`, `capacity-v114.test.ts` |
| A revoked device cannot reuse an existing session | session store | `session-loss-v114.test.ts` |
| A revoked device stops reconnecting | `sse-client.ts` | `sse-reconnect-v114.test.ts` |
| A Client PC keeps no authoritative business data | client isolation | `client-isolation-v114.test.ts` |
| A role-stamped client database is refused by backup/restore | database boundary | `db-boundary-v114.test.ts` |

## 6. Owner physical tests still pending

Device licensing is verified by automated tests on Linux and Windows, but the *physical* cases are
**PENDING OWNER PHYSICAL TESTING** (rows T18–T29 of `V1.1.4_WINDOWS_TWO_PC_VERIFICATION.md`):
second PC pairing and approval, approval beyond capacity on real hardware, revocation while the
client is trading, DPAPI key persistence across a reboot, and a client trying to talk to an
impostor main PC with a mismatched certificate pin.
