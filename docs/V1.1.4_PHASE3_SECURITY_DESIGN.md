# V1.1.4 — PHASE 3 SECURITY & ARCHITECTURE DESIGN

Status: **design for review** · Author: Arena agent · Date: 2026-11-04
Scope: Phase 3 of `docs/V1.1.4_AUDIT.md` — authenticated LAN API, TLS, device identity, SSE.
This document is written **before** the code and is superseded by evidence, never by intent.

---

## 0. Non-negotiable invariants

1. A device is trusted only if **all** of these hold: valid vendor signature, same store,
   enrolled + **approved by a Main PC administrator**, an unrevoked credential, and a live session.
   A licence or a Store ID alone is never sufficient.
2. Clients never open, read or copy the SQLite file. Every business fact arrives through the API.
3. The vendor private signing key never enters the Main App, the installer, the repo, logs,
   diagnostics or test fixtures.
4. Every write is authorised on the server from its own user table + device registry.
5. No endpoint is "trusted because the UI would not call it".

---

## 1. `/api/v1` — endpoints, contracts, authorization

### 1.1 Shape

```
POST /api/v1/auth/login          {device_id, username, password}        → {session, user, store, expires_at}
POST /api/v1/auth/logout         —                                       → {ok}
GET  /api/v1/server/info         —                                       → {server_id, store_id, name, version, capacity, fingerprint}
GET  /api/v1/server/health       —                                       → {state, clients, db_ok, uptime}
POST /api/v1/pairing/claim       {code, device}                          → {status: pending|approved, device_token?}
GET  /api/v1/devices/self         —                                      → device record + approval status
POST /api/v1/rpc                 {method, args, idempotency_key?}        → the existing authorised route table
GET  /api/v1/events              (SSE, Last-Event-ID)                    → event stream
```

`POST /api/v1/rpc` intentionally reuses the 249-route table that already enforces permissions
server-side. Phase 3 wraps it in device authentication; it does **not** invent a second business
layer that could drift from the desktop app.

### 1.2 Per-request pipeline

```
TLS handshake (pinned)  →  device credential (header x-sauda-device + HMAC signature)
   →  replay window (nonce + timestamp)  →  session lookup (device-bound, persisted)
   →  permission check on the host  →  idempotency (writes)  →  service call
   →  audit(device_id, user_id, method)  →  response  →  outbox event
```

Any failure stops the pipeline; the service layer is never reached.

### 1.3 Contracts

- Bodies are JSON, ≤ 1 MB. Unknown fields are rejected on sensitive endpoints (`/auth`, `/pairing`).
- Errors are `{ok:false, code, message}` with a stable `code` (`AUTH_REQUIRED`, `DEVICE_PENDING`,
  `DEVICE_REVOKED`, `PAIRING_EXPIRED`, `REPLAY`, `BAD_SIGNATURE`, `FORBIDDEN`, `RATE_LIMITED`,
  `IDEMPOTENCY_CONFLICT`, `TRANSPORT_REQUIRED`, `SERVER_BUSY`).
- No raw database rows: every response is built by the same DTO functions used over IPC.

### 1.4 Authorization boundaries

| Boundary | Enforced by |
|---|---|
| Is this a known, approved, unrevoked device? | device credential + registry (`terminals`) |
| Is this request fresh (not replayed)? | nonce/timestamp window + nonce cache |
| Is this user allowed to do this? | host-side permission check on the route |
| Is this device allowed to do this now? | session must belong to the same device |
| Is the request safe to retry? | idempotency key, response replay |

A device may only ever see data the **logged-in user** could see on the Main PC. Device role
(`SERVER_POS`/`CLIENT_POS`/`CLIENT_MANAGEMENT`) narrows the surface further: a management device
gets reporting/settings routes, a POS device gets selling routes.

## 2. TLS: generation, trust, pinning, rotation, recovery

### 2.1 Generation (no new dependency)

The Main PC generates, on first server start:

- an RSA-2048 keypair (or P-256 if the platform prefers ECDSA), and
- a self-signed X.509 v3 certificate built in `packages/core/src/net/certificate.ts` with a small
  hand-written DER encoder, because Electron ships no certificate authority and a runtime `openssl`
  dependency is not guaranteed on Windows.

Subject `CN=Sauda Store <store_id>`; SANs: `localhost`, `127.0.0.1`, and every current LAN IPv4
address of the host (re-generated when the address set changes). Validity 5 years, `keyUsage:
digitalSignature,keyEncipherment`, `extKeyUsage: serverAuth`, `basicConstraints: CA:FALSE`.

The certificate and key are stored in `<data>/tls/` (key file mode 0600 on POSIX; on Windows the
file inherits the per-user profile ACL). The SHA-256 **fingerprint of the DER certificate** is the
value clients pin.

### 2.2 Trust establishment

First contact (pairing) carries the fingerprint inside the QR payload, itself only obtainable from
the Main PC's screen or an admin-approved pairing code. The client stores the fingerprint with the
saved server profile. Subsequent connections must present a certificate whose SHA-256 equals the
pinned value; a mismatch aborts the connection with `CERT_MISMATCH` and **never** falls back.

Manual-IP connections display the fingerprint and require the operator to compare it with the one
shown on the Main PC before saving — a deliberate human confirmation step, documented in the UI.

### 2.3 Rotation

An administrator can regenerate the certificate (expiry, compromise, hardware change). Rotation:

1. creates the new pair, keeping the old one for a grace window;
2. shows the new fingerprint on the Main PC and requires approval of each client re-pin;
3. records `cert_rotated_at` and an audit entry;
4. clients that have not re-pinned fail closed with a clear message, never with silent trust.

### 2.4 Recovery

If the certificate file is lost but the store database is intact, a new certificate is generated and
the fingerprint changes — every client must re-pin. If the **store identity** is lost (database
restored from another shop), the server refuses to start serving devices whose licence `store_id`
does not match, so a mistaken restore cannot silently impersonate another shop.

## 3. Device identity, credentials, authentication, revocation

- **Device key**: every client generates an Ed25519 keypair on first run. The private key is kept in
  a DPAPI-protected file on Windows (`packages/app/electron/secure-store.ts`, Phase 3 milestone B);
  the sandbox path (non-Windows) uses a 0600 file and is documented as a development fallback.
- **Enrolment**: the client presents `{device_id, public_key, licence}` to `/pairing/claim`; the
  server verifies the vendor signature, the store binding and the capacity, then creates a
  `pending` terminal. **Nothing else is issued at this point.**
- **Approval**: an administrator on the Main PC approves; only then does the server mint a device
  credential: a 32-byte secret, stored only as a SHA-256 digest in `terminal_credentials`.
  The plaintext is returned once, over TLS, and stored by the client under DPAPI.
- **Authentication**: every request carries `x-sauda-device: <device_id>`, `x-sauda-ts`, `x-sauda-nonce`
  and `x-sauda-sign: HMAC-SHA256(device_secret, method‖path‖ts‖nonce‖sha256(body))`.
  The server recomputes it; a mismatch is `BAD_SIGNATURE`.
- **Revocation**: `revokeDevice()` deletes the credential, revokes every session and marks the
  licence `revoked`. A revoked device gets `DEVICE_REVOKED` on its next request and cannot re-enrol
  itself (Phase 1 rule, tested).
- **Rotation**: `issueDeviceSecret()` replaces the digest; the old secret stops working immediately.

The device's Ed25519 public key is recorded at approval time for future request signing; the HMAC
credential is the Phase 3 authentication mechanism because it needs no extra round-trip and is
constant-time verifiable.

## 4. Replay protection, signing, idempotency, authorization

| Mechanism | Rule |
|---|---|
| Timestamp window | `|now − ts| ≤ 120 s`, otherwise `STALE_REQUEST` |
| Nonce | 16 random bytes, remembered for the window; a repeat is `REPLAY` |
| Signature | HMAC over method, path, timestamp, nonce and body digest (above) |
| Body binding | the digest is part of the signature, so a tampered body fails |
| Idempotency | `Idempotency-Key` required for POST writes; replay returns the stored response (Phase 1 helper), same key + different body is `IDEMPOTENCY_CONFLICT` |
| Authorization | route permission resolved from the server's user table; device role narrows the route set |
| Rate limits | per device: 60 req/s burst, 10 login failures / 15 min; per address as today |

Transport encryption alone is never treated as authentication: the HMAC is verified even inside TLS.

## 5. SSE: authentication, reconnection, sequence recovery, authorisation

- `GET /api/v1/events` requires the same device HMAC + session as any other call. A browser cannot
  set custom headers on `EventSource`, so the Electron client uses `fetch()` with a streaming reader
  instead of the `EventSource` class — this keeps the signature mechanism uniform.
- Each event is `{seq, event_id, type, entity_id, payload, schema_version, created_at}` from the
  `event_outbox` written in the business transaction.
- The client stores the last `seq`; reconnection sends `Last-Event-ID` and the server replays from
  `seq + 1`. A gap larger than the retention window returns `RESYNC_REQUIRED`, and the client runs a
  full authoritative refresh before resuming — events are an optimisation, never the source of truth.
- Authorisation: events are filtered by the device's role and the user's permissions; a POS device
  does not receive accounting or cost events it could not otherwise fetch.

## 6. LAN threat model

| Threat | Mitigation | Residual risk |
|---|---|---|
| Hostile device on the LAN | no request without a device credential; unknown devices rejected before any service call | a compromised *approved* device is inside the trust boundary |
| Server spoofing (fake Main PC) | pinned certificate fingerprint; manual connections require human fingerprint confirmation | user confirms the wrong fingerprint — mitigated by showing a short verification phrase |
| Replay of a captured request | timestamp window + nonce cache + HMAC over body | within-window replay of a *different* request is impossible; same request is blocked by the nonce cache |
| Credential theft (disk) | device secret stored under DPAPI; server stores only digests | an attacker with the live user session can act as that user |
| Unauthorised enrolment | admin approval required; capacity enforced; revoked devices cannot re-enrol | a social-engineered admin approval |
| Client isolation / wrong subnet / firewall | explicit diagnostics on the client, distinct error codes, no silent retry storm | network misconfiguration is a support issue |
| DoS (flood, half-open) | body cap, per-device rate limit, connection limit, request timeout | a LAN-level flood is outside application control |
| Downgrade to plaintext | HTTP listener refuses `/api/v1` without TLS (`TRANSPORT_REQUIRED`); legacy AES-GCM `/rpc` remains only for the v1.1.3 compatibility window and is removed when no v1.1.3 terminal exists | mixed-version shops during upgrade |
| Log leakage | audit stores device id, user, method and outcome — never bodies, secrets or licence payloads | OS-level log access |

## 7. Pairing and administrator approval

1. Admin opens **Devices → নতুন ডিভাইস**, the Main PC requests a pairing code:
   192 bits, single use, 2-minute TTL, stored as a digest (`pairing_tokens`, Phase 1).
2. The screen shows a QR: `{protocol: 3, host, port, store_id, server_id, cert_fp, code, expiry}`.
   No password, no reusable token.
3. The client scans/submits the code, verifies the certificate fingerprint, generates its keypair and
   calls `/pairing/claim`. The server consumes the code (single use), verifies the licence, checks
   capacity and creates a `pending` row.
4. The Main PC shows the pending request with device name, licence id, OS and time. The admin
   approves or rejects; the decision is audited with the deciding user.
5. Only after approval does the client receive its credential and can log in.

A code can be re-issued at any time; the previous code becomes invalid the moment a new one is
created (single active code per store).

## 8. Offline behaviour and expiry

| Situation | Client behaviour | Server behaviour |
|---|---|---|
| Server unreachable | keep the cart draft locally, disable commit, show `Disconnected`; no queueing of completed sales | rejects nothing (it is down); sessions simply expire |
| Session expiry | `AUTH_REQUIRED` → login screen; draft survives | sliding TTL (12 h), persisted in `terminal_sessions` |
| Credential expiry/rotation | `BAD_CREDENTIAL` → pairing screen, never silent retry | old digest removed immediately |
| Device revoked mid-session | next request fails; UI returns to pairing | sessions revoked in the same transaction |
| Certificate rotated | `CERT_MISMATCH` → shows both fingerprints and asks the operator | serves only with the new certificate after rotation |
| Clock skew | `STALE_REQUEST` after 120 s → client resyncs from `/server/info` | does not widen the window automatically |

## 9. Compatibility with v1.1.3 data and the Phase 1/2 foundation

- Schema v5 is untouched by Phase 3; no new tables are required for TLS (certificate + fingerprint
  live in `store_servers.cert_fingerprint` and the two files in `<data>/tls/`).
- Licence payload v1 keeps working; a shop with a v1 licence is a standalone POS and never needs the
  LAN API. Payload v2 adds `store_id`/`device_id`/`device_role`/`device_capacity` — required only for
  multi-PC enrolments.
- The existing `/rpc` AES-GCM transport stays during the migration window so a v1.1.3 terminal is not
  bricked, but it can only reach routes that a v1.1.3 host already exposed, and it is refused by a
  v1.1.4 host once `require_tls = 1` (default for new installs, opt-in for upgraded hosts).
- No customer data is rewritten by Phase 3. The only writes are new rows in the Phase 1/2 tables.

Milestone A is implemented and tested in this phase; B–E follow in separate commits so each can be
reviewed and reverted independently.

## 11. Explicitly out of scope for Phase 3

Public-internet exposure, WAN replication, cloud sync, certificate authorities, SSO, and any change
to the accounting or stock logic.
