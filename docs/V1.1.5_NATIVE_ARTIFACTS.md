# V1.1.5 — native artifacts (A-11)

What ships inside the installers besides our own JavaScript, where it came from, what was checked,
and what is **not** proven. Every number here was printed by `node scripts/audit-native.mjs` on the
tree this document describes; re-run it on the packaging machine to compare.

## 1. What was wrong

Both installers carried **eight** better-sqlite3 prebuilt binaries — 17.0 MiB uncompressed — for a
product whose only installer target is Windows x64 (`win.target = [{ target: 'nsis', arch: ['x64'] }]`
in both package manifests). Seven of the eight can never be loaded by anything a customer runs, and
none of them are ever executed on the build machine.

## 2. Provenance

- **Package:** `better-sqlite3@13.0.3`, declared as a production dependency of **both** packages.
- **Source:** `https://registry.npmjs.org/better-sqlite3/-/better-sqlite3-13.0.3.tgz`, recorded in
  `package-lock.json` with the integrity `sha512-RbOBxmLBG8uvFUc15X9+9SFemKcQ0WBuISBVkpuiaUB2qblC8UWlHEjdWVoZ8AdhSwmoEgsiXKfopX0CQxaACQ==`.
  npm verifies that hash when it downloads the tarball, so the files in `node_modules` are the bytes
  the registry published — provided `npm ci` was the install path, which is what both CI workflows
  use.
- **Not downloaded separately:** v1.1.5 installs with `--ignore-scripts` in this environment (the
  node-gyp toolchain cannot reach the network here), so the prebuilds present are exactly the ones
  inside the vendor tarball. `scripts/audit-native.mjs` re-checks the lock entry against the
  installed `package.json` version on every `npm run verify`.

## 3. Reproducibility from source — **not established**

Stated plainly, because this is the part an audit is tempted to hand-wave:

- better-sqlite3 can be compiled from source, and the vendor publishes the source in the same
  tarball (`src/`, `deps/sqlite3`). Reproducing the *published* binaries bit-for-bit would require
  the same MSVC/Clang versions, flags and `SQLITE_*` defines the vendor used. **That was not done
  here** — there is no Windows toolchain in this environment and the node-gyp headers cannot be
  fetched.
- What *is* established is the chain: tarball SRI (npm) → recorded per-file SHA-256 (this audit) →
  the same hashes can be compared on the packaging machine before a release.
- The shipped app does not rely on these bytes anyway: electron-builder rebuilds native modules for
  Electron's ABI during packaging (`npmRebuild` is not disabled), producing
  `node_modules/better-sqlite3/build/Release/better_sqlite3.node`, which is what Electron loads and
  which `asarUnpack` (`**/node_modules/better-sqlite3/**`) keeps outside the asar archive. The
  prebuilds are a development/Node fallback.
- **Windows compatibility evidence:** the Windows CI job runs the full suite, which opens real SQLite
  databases through this module, on `windows-latest` x64. That proves better-sqlite3 13.0.3 works on
  the shipped platform — it does **not** prove byte-identity with the file in the installer, because
  CI builds or downloads its own binding. The installer-level check remains part of the blocked VM
  gate.

## 4. Secret and payload scan

`scanBinary()` reads each binary as bytes and looks for private-key headers (RSA, PKCS#8, EC,
OpenSSH) and for our own product key marker. Result on this tree: **no findings**. The scan is
repeated by `scripts/audit-native.mjs` on every `npm run verify`, and the repository-wide
`security-v113.test.ts` independently refuses a tracked private key anywhere in `packages/` or
`scripts/`. The detector assembles its own search strings from parts so that it does not trip that
guard with its own source.

## 5. The fix

`scripts/lib/native-artifacts.mjs` gains `pruneForeignPrebuilds()`, called by **both**
`scripts/package-app.mjs` and `scripts/package-license-generator.mjs` immediately before
electron-builder runs:

- it keeps `prebuilds/win32-x64.node` and deletes the other seven;
- it **refuses to run** if the Windows x64 binary is missing, so packaging fails loudly instead of
  producing an installer whose database binding cannot load;
- it is idempotent, so re-running the packaging step is harmless;
- nothing else in the tree is touched (`build/Release`, `src/`, `deps/` are left alone — the vendor
  rebuild and any source build still work).

Measured impact of the rule: **7 binaries, 14.2 MiB uncompressed**, no longer reach either installer.

**What is not claimed here:** the installer's on-disk size delta. Compression of `.node` files is not
linear, and the NSIS output can only be measured by a packaging run on Windows, which this
environment cannot do (the VM gate is blocked). The rule and its effect on the packaged file list are
tested; the byte count is not.

## 6. Tests

`scripts/tests/native-artifacts.test.mjs` (10):

| Test | What it refuses |
| --- | --- |
| header reader | a PE/ELF/Mach-O machine read from the file name instead of the header |
| prune | a Darwin, Linux or Windows-arm64 binary surviving into the installer |
| idempotence | a second packaging pass failing or deleting the kept binary |
| missing Windows binary | packaging continuing with no loadable binding |
| dry run | the audit mutating `node_modules` |
| inventory | more than one prebuild marked loadable on Windows x64 |
| secret scan | private-key material inside a shipped binary going unreported |
| provenance | a dependency with no lock SRI record being treated as verified |

## 7. Remaining exposure

- The pruning is exercised by tests and by the release workflow's packaging step, but **no installer
  produced after this change has been built in this environment**. The size delta and the file list
  inside the NSIS package must be confirmed on the first real packaging run.
- Reproducing the vendor binaries from source is not attempted; the audit ties them to a registry
  tarball by SRI instead, which is a weaker but honest claim.
- Authenticode status is unchanged (unsigned, accepted under the v1.1.4 policy).
