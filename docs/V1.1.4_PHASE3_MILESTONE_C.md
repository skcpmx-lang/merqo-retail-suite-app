## 2. Contract

```
GET /api/v1/events
  x-sauda-device / x-sauda-ts / x-sauda-nonce / x-sauda-sign   (Ed25519, as every /api/v1 call)
  x-sauda-session: <session token>        (or ?session=)
  Last-Event-ID: <seq>                    (or ?last_event_id=; absent = live only)
→ 200 text/event-stream
  id: <outbox seq>
  event: sale.created | inventory.updated | …
  data: {…payload…}
```

* **Authorisation on every connection:** device signature, approved device, session bound to that
  device. A pending/revoked device is refused before the stream opens.
* **No browser access by design:** an `EventSource` cannot attach signature headers, so only the
  Electron main process (a signer) can subscribe. There is no separate stream token.
* **Monotonic sequence:** the SSE `id` is the outbox `seq` (AUTOINCREMENT), so ordering is the
  database's order, not a timer's.
* **Resume:** `Last-Event-ID` replays only `seq > id`, so a reconnect yields exactly the missed events
  — no duplicates (the client also drops any id it already saw).
* **Gaps are surfaced, not hidden:** if the next id jumps (e.g. an event for another store was filtered
  out), the client calls `onGap(from, toInclusive)` so the caller can refetch.
* **Revocation terminates the stream:** the stream re-checks device status and session validity on
  every poll (25 ms–1 s) and heartbeat, and `LanApi.closeStreams(deviceId)` closes it immediately.
* **Server restart / network drop:** the stream ends, the client reconnects with the same signature and
  `Last-Event-ID`, and the events written during the outage are delivered from the outbox.
* **Cross-store isolation:** the outbox is filtered by `store_id` in the query *and* per event before
  writing, so another store's event cannot leak even on a shared database file.
* **No silent downgrade:** `openEventStreamClient` throws for any non-`https` base URL, and the server
  never serves `/api/v1` without TLS.

## 3. Test evidence (12 tests, all real network + SQLite)

Authorisation: unsigned stream → `MISSING_SIGNATURE` · no session → `AUTH_REQUIRED` · another device's
session → `SESSION_DEVICE_MISMATCH` · revoked device → `DEVICE_REVOKED` (and `streamCount() === 0`, so
nothing was opened).

Delivery: new events arrive in order with `id` equal to `seq` · another store's event is never
delivered (asserted on both the payload and the count) · resume from `Last-Event-ID` delivers exactly
the two missed events, no duplicates · revoking a device closes an open stream (server sees the
revocation without any push channel) · server stop closes the stream.

Client: refuses `http://` · reconnects by itself after a real server restart on the same port and
receives the event written during the outage (no gap reported) · reports a gap when the sequence jumps
across a filtered event.

## 4. NOT VERIFIED

| Item | Manual procedure |
|---|---|
| Stream across two physical PCs | open the client on PC-B, create a sale on PC-A, confirm it arrives within ~1 s; pull PC-B's cable, make 3 sales on PC-A, reconnect: all 3 must arrive exactly once |
| Behaviour with Wi-Fi sleep / roaming | put PC-B to sleep for 5 minutes, wake it: stream must resume with no duplicates and no missing sales |
| Windows Firewall / AP isolation | confirm the failure shows as a network error and the app does not silently fall back to HTTP |
| Long-lived stream stability (hours) | leave both PCs running for a shift; confirm no memory growth in the Main app and no duplicate deliveries |
| Revocation latency on hardware | revoke PC-B from the Main PC; the stream must close within the heartbeat interval and the UI must say the device was revoked |

## 5. Open risks

1. Polling interval decides delivery latency (default 1 s). Fine for shop scale; not a push bus.
2. Each stream holds a socket; the current capacity model does not bound concurrent streams per
   server. With a licensed maximum of a handful of devices this is acceptable, but there is no
   explicit limit yet.
3. `?session=` is not covered by the signature (it is device-bound and single-use via the nonce).
   The preferred transport is the header; the query form exists for tooling.
4. No event compaction: the outbox grows until the (future) retention job exists.
