### Why `withIdempotencyAsync` exists

The synchronous helper would have stored the *pending Promise* of an `async` handler and replayed
`{}` instead of the real answer. The API tests caught exactly that (first call 200 with `data: 1`,
retry 403 with an empty body). The async variant awaits first, then persists the resolved response;
the original synchronous helper is unchanged so Phase 2 behaviour and its tests are untouched.

## 2. `/api/v1` surface

TLS is **mandatory**: `startLanApi` throws `TLS_REQUIRED` if certificate material is not supplied —
there is no plaintext mode to fall back to.

| Method | Route | Device signature | Session | Purpose |
|---|---|---|---|---|
| GET | `/api/v1/server/info` | not required | not required | protocol version, app version, store id, server id, licensed/used capacity — **no secrets, no licence payload** |
| POST | `/api/v1/pairing/claim` | not required (key is in the body) | not required | `{code, device_id, device_name, public_key, license_id}` → `202` pending, `410` expired/used, `409` store mismatch or capacity full |
| GET | `/api/v1/devices/self` | required | not required | own record + status (a *pending* device may read only this) |
| POST | `/api/v1/auth/login` | required | — | returns a session **bound to the device id** |
| POST | `/api/v1/rpc` | required | required | existing method table, unchanged permission checks, optional `idempotency_key` |

Every route additionally requires the JSON body to be a plain object under the existing 2 MB cap and
content type `application/json`; anything else is `BAD_REQUEST`.

### Signing scheme (supersedes the design document's HMAC description)

The design document (`docs/V1.1.4_PHASE3_SECURITY_DESIGN.md`) originally described an HMAC shared
secret. A shared secret means the server can impersonate every device and a stolen server-side
secret breaks all devices at once, so Milestone B implements **Ed25519 public-key signatures**
instead:

* The device generates a keypair locally (`generateDeviceKeyPair`, PKCS#8 private / SPKI public).
  The **private key never leaves the device** and is not sent at pairing — only the public key is.
* Public key is stored in `terminals.public_key` (SPKI, base64). Server keeps no private key for
  devices, so a database leak cannot be used to sign as a device.
* Canonical string: `METHOD \n path \n timestamp \n nonce \n sha256(body)`; headers
  `x-sauda-device`, `x-sauda-ts`, `x-sauda-nonce`, `x-sauda-sign`.
* ±120 s clock skew window; nonces are tracked in an in-memory `ReplayGuard` keyed `device:nonce`.
* Missing headers are rejected **before** the device lookup, so the answer is `MISSING_SIGNATURE`
  rather than leaking whether a device id exists.

Error codes: `MISSING_SIGNATURE`, `STALE_REQUEST`, `REPLAY`, `BAD_SIGNATURE`, `NO_DEVICE_KEY`,
`UNKNOWN_DEVICE`, `DEVICE_PENDING`, `DEVICE_REVOKED`, `SESSION_DEVICE_MISMATCH`,
`AUTH_REQUIRED`, `FORBIDDEN`, `PAIRING_EXPIRED`, `PAIRING_USED`, `STORE_MISMATCH`, `BAD_KEY`,
`IDEMPOTENCY_CONFLICT`, `TLS_REQUIRED`, `BAD_REQUEST`.

Rejections are written to the audit log with the code and device id, so a hostile device hammering
the port leaves a trail even though it never gets a session.

## 3. Certificate persistence and recovery

| Situation | Behaviour | Code |
|---|---|---|
| files absent, `allowCreate: true` (first boot) | generate, write `server.crt` + `server.key`, mode `0600` on POSIX | — |
| files absent, `allowCreate: false` | refuse; never silently invent an identity | `IDENTITY_MISSING` |
| unreadable file (permissions/IO) | refuse | `IDENTITY_READ_FAILED` |
| unparseable or half-written certificate | refuse; no auto-regeneration | `IDENTITY_CORRUPT` |
| certificate-only or key-only directory | refuse | `IDENTITY_CORRUPT` |
| stored fingerprint ≠ expected pin | refuse | `IDENTITY_MISMATCH` |
| certificate does not match its key | refuse | `IDENTITY_MISMATCH` |
| explicit `rotateServerIdentity()` | new identity, previous files kept as `server.crt.old` / `server.key.old`, new pin returned | — |

Refusing instead of regenerating is the point: a silent regeneration would invalidate every pinned
client, and would also hide tampering.

**Evidence (automated):** "keeps the same fingerprint across restarts and reuses the files",
"refuses to invent an identity when it is missing", "reports a corrupt certificate instead of
regenerating it", "refuses a half-written identity", "detects a replaced certificate (different
fingerprint)", "detects a mismatched certificate/key pair", "rotates explicitly, keeps the old
files, and changes the pin" — 7 tests, all using a temporary directory and real files.

**Not verified:** Windows ACLs on `server.key` (mode `0600` is POSIX; on Windows the profile ACL is
relied on), and real rotation on hardware. The rotation *code path* is tested; the claim "the old
certificate stops working for already-paired clients on Windows" is **not** verified.

## 4. Security test matrix (negative-first)

All 27 tests are integration tests: a real HTTPS listener on a loopback port, a real SQLite file,
real Ed25519 keys, real HTTP requests made with Node's `https` module using the server certificate
as the trust anchor.

| Attack / condition | Expected | Test |
|---|---|---|
| Read server identity | id/version/capacity returned, **no secret, no licence payload** | serves identity without any secret or licence payload |
| Start without TLS | refuses to start | refuses to start without TLS material |
| Unknown device id | `UNKNOWN_DEVICE`, method never runs | rejects an unknown device before any route runs |
| No signature headers at all | `MISSING_SIGNATURE` (no existence leak) | rejects a missing signature |
| Body altered after signing | `BAD_SIGNATURE` | rejects a tampered body (signature covers the body digest) |
| Old timestamp | `STALE_REQUEST` | rejects a stale timestamp and a replayed nonce |
| Same nonce replayed with a fresh timestamp | `REPLAY` | (same test) |
| Pending device | may read own status only, everything else `DEVICE_PENDING` | rejects a pending device but lets it read its own status |
| Revoked device with a *valid* signature | `DEVICE_REVOKED` | rejects a revoked device even with a valid signature |
| Device signing with a key it does not own | `BAD_SIGNATURE` | rejects a device whose signing key does not match the registered key |
| Login | session issued, bound to device, allowed route works | logs in, binds the session to the device, and enforces route permissions |
| Session without permission | `FORBIDDEN` | refuses a route the user has no permission for |
| `/rpc` without a session | `AUTH_REQUIRED` | requires a session for /rpc |
| Pairing code replayed | second claim `PAIRING_USED`, one device only | accepts a code once, creates a pending device, and rejects the replay |
| Licence from another store | `STORE_MISMATCH` | rejects a licence from another store |
| Expired pairing code | `PAIRING_EXPIRED` | rejects an expired pairing code |
| Malformed / non-Ed25519 public key | `BAD_KEY` | rejects a malformed public key |
| Same idempotency key, same body | first answer returned, no second side effect | returns the first answer for a repeated key and conflicts on a different body |
| Same key, different body | `IDEMPOTENCY_CONFLICT` | (same test) |
| Concurrent writes | counter ends at the exact expected value, no duplicate, no loss | serialises concurrent writes without duplicating or losing a counter |
| Restart | same fingerprint, files reused | certificate persistence tests (7) |
| DB after the whole suite | passes `PRAGMA integrity_check`, tables intact | leaves the shop database healthy |
| Approval lifecycle | pending device rejected, usable after administrator approval | becomes usable only after administrator approval |

Deliberate non-shortcuts: no test asserts a 200 for a request that should fail, no test disables TLS,
no test bypasses the permission table. Where a test needed a *successful* call (idempotency, replay),
it first obtains a real session through `/api/v1/auth/login` — it does not stub authentication.

## 5. Bug found and fixed in Milestone A code (certificate serial)

While chasing an intermittent failure of the whole suite (roughly 1 run in 8), a **real defect in the
Milestone A certificate generator** was found, not a test problem:

* Symptom: `error:068000DD:asn1 encoding routines::illegal padding` thrown from
  `https.createServer` / `tls.createSecureContext`, so the server could not start at all.
* Reproduction: generating certificates in a tight loop until the failure appears — about **1 in
  256** certificates (2 failures in ~900 certificates across 4 parallel workers; captures at
  generation 132 and 307 of one 500-iteration run).
* Cause: the 16-byte random serial was encoded with `der.integer()` as-is. When the serial's first
  byte is `0x00`, the certificate carried a **non-minimal DER INTEGER** (leading padding byte), which
  OpenSSL rejects. 1 in 256 first boots would therefore have failed to create an identity at all.
* Fix: `der.integer(Buffer)` now strips redundant leading zeros (keeping the required `0x00` only
  when the high bit is set, to keep the value positive).
* Regression tests (2 new): a serial of `00 00 5C …` must produce serial number `5C…` and a serial of
  `FF 01 …` must keep its leading zero; plus a 40-certificate sweep asserting every generated
  certificate loads in `tls.createSecureContext`.
* Re-verification: 4 Parallel workers × 400 certificates = **1600 certificates, 0 failures**
  (same harness that produced 2 failures before the fix).

This is the honest version of "the tests caught something": the failing assertion was in a Milestone A
test, the fault was in Milestone A production code, and the fix is a one-line change plus tests. The
test suite was re-run **5 times consecutively after the fix: 358 passed / 29 files, 5/5 green**.

## 7. Remaining risks

1. **Replay guard is in memory.** A server restart clears seen nonces; the ±120 s timestamp window is
   then the only replay bound. Persisting nonces is a Milestone C item.
2. **Clock skew.** Devices with badly wrong clocks fail with `STALE_REQUEST`. The UI does not yet
   tell the user to fix the device clock.
3. **`/api/v1` is not yet used by the renderer.** The Electron app still talks to the server through
   IPC/`/rpc`. The legacy `/rpc` tunnel is still present; retiring it is Milestone D and must not
   happen before the renderer is migrated (otherwise existing installs break).
4. **No SSE/event stream yet** (Milestone C). Clients still refetch.
5. **Capacity and pairing are tested only through the API**, not through the device-management UI
   (that screen does not exist yet, K1 in the matrix).
6. **Nonce and rate limits are per-process.** A multi-process deployment is not supported or tested.
7. **Private-key storage on the device** is not implemented (L7 / DPAPI) — devices do not yet
   persist their key pair between runs, so a device must re-pair or re-register its key. This is the
   largest open item before any real two-PC trial.

## 8. Not verified — manual procedure required (two Windows PCs)

Everything below is **BLOCKED in this sandbox**: no Windows, no Electron runtime, no second machine,
no DPAPI, and no physical network.

1. **TLS between two PCs.** On PC-A start the Main Server in developer mode; copy the certificate
   fingerprint shown on the Settings screen. On PC-B run the device client against
   `https://<PC-A-LAN-IP>:<port>`. Expected: connects only when the pin matches; after editing the
   fingerprint by one character the connection must fail with a pin mismatch and the UI must show an
   error rather than a blank screen. Record both outcomes verbatim.
2. **Certificate persistence across a Windows restart.** Start the server, note the pin, quit the
   app, start it again. Expected: identical pin, `server.crt`/`server.key` untouched in the profile
   directory. Then delete `server.key` only, restart: expected explicit *corrupt identity* error, not
   a silent new certificate.
3. **Windows ACL on the key file.** Check `icacls server.key` — only the installing user and SYSTEM
   may read it. Record the output.
4. **Pairing + approval.** Claim with a fresh code from PC-B; expect *pending* and no data access on
   PC-B. Approve on PC-A; expect PC-B to work without a restart. Replay the same code from a third
   client: expect `PAIRING_EXPIRED`/used, one device row only.
5. **Revocation.** Revoke PC-B from PC-A. Expect PC-B's next call to fail with a revoked-device error
   and its session to stop working immediately.
6. **Wrong clock.** Set PC-B's clock 10 minutes back and try to log in; expect `STALE_REQUEST` with a
   readable message.
7. **Firewall / client isolation.** With "AP isolation" enabled on the router, confirm the failure is
   reported as a network error and not as a credential error.
8. **Hostile device.** From a PC that knows the store id and holds a valid shop licence, attempt a
   call with no signature and with a forged one. Expected: rejected, and an audit row for each
   rejection. This is the specific check that a licence alone never grants access.
