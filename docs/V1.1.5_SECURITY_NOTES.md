# V1.1.5 — security notes

Written for the shop owner and for whoever supports the installation. It states what the software
protects, how, and what it does **not** protect — no more and no less.

## 1. What was reviewed for this release

| Area | What was checked | Result |
| --- | --- | --- |
| Licence signing | Ed25519 signature verified **before** anything else in a licence is trusted; payload schema validated; expiry enforced; device binding matched with weighted hardware scoring; a clock-rollback guard refuses an expired licence when the system clock is moved back | reviewed, no defect found |
| Key material | private key never in the app, installers, Git, CI, logs or chat; both release gates scan tracked content and packaged files for `BEGIN PRIVATE KEY` and for key-override environment variables | reviewed; the secret scans are part of `npm run verify` and run again on the packaged installers in `release.yml` |
| LAN transport | TLS with certificate pinning on the client side; Ed25519 device signatures on every request; sessions bound to a device; replay protection persisted across restarts; the legacy shared-token listener is loopback-only | reviewed; the v1.1.5 change here is the shutdown guard (A-04), which stops a stream being registered while the server stops |
| Authorisation | every IPC route declares a permission and the wrapper enforces it; the same permission set is used by the LAN RPC table, so desktop and LAN cannot disagree; the renderer never opens the database | reviewed |
| Money integrity | integer arithmetic throughout; credit limits, price floors and discount caps enforced server-side; stock adjustments now atomic (A-01); serials bound to their product (A-13) | reviewed, three defects fixed |
| Data at rest | SQLite with WAL; the database file is not encrypted — see §3 | accepted, documented |
| Backups | SHA-256 manifest, integrity check before and after, client-database refusal, reversible restore (A-14), unique file names (A-15) | reviewed, two defects fixed |
| Dependencies | `npm audit --omit=dev` in the release gate: 0 high/critical/moderate in production dependencies | clean at baseline and at release |
| Installers | verified for version metadata, x64 architecture, absence of key material, and SHA-256; published assets are re-downloaded and re-verified before the draft is promoted | enforced by `release.yml` |

## 2. What the software does to protect the shop

- **Only the Main PC can write.** Clients talk to it over an authenticated TLS API. There is no
  shared database file to corrupt and no second writer.
- **No device trades until an administrator approves it.** A stolen Client PC cannot join a shop by
  itself, and revoking a device removes its session within one poll interval.
- **Every money-moving action needs a permission.** Cashier, manager and admin are enforced in the
  service layer, not in the UI, so a modified client cannot bypass them.
- **Every consequential action is audited** with the user, the time and the details — a permanent trail
  for cash, stock, prices, discounts, voids, returns and settings.
- **Nothing leaves the machine.** No telemetry, no cloud call, no remote logging.

## 3. What it does **not** protect against — read this

| Risk | Reality | What to do |
| --- | --- | --- |
| Someone with the database file | The SQLite file is **not encrypted**. Anyone who can copy it can read the shop's data | keep the PC physically secure, use a Windows account with a password, and keep backups on a device you control |
| A determined local attacker | A user who is an administrator on the PC can modify the app or the database | restrict who has Windows administrator rights; the app's own roles are not a defence against an OS administrator |
| Unsigned installers | There is no Authenticode signature, so Windows cannot prove where the file came from | verify the SHA-256 against `SHA256SUMS.txt` before every install or upgrade |
| SmartScreen | An unsigned installer has no reputation; Windows may warn on first run | the warning is expected; proceed only after the hash matches |
| Offline revocation | A revoked licence keeps working until expiry on an already-activated PC | plan renewals; do not rely on revocation for immediate lockout |
| Physical access to a logged-in till | An unattended, unlocked POS can be used by anyone | lock the screen; use per-person users so the audit trail names the right person |
| Antivirus interference | Some scanners hold files open; the app now fails a restore safely instead of losing the database | if a restore or backup fails, read the message: it names the file that was kept |

## 4. Report a problem

If you find a security issue, contact the vendor through the support channel used for your licence.
Please include the version (About screen), what you did, and what happened. Do not attach the shop
database or any licence file to a support message unless the vendor asks for it in writing.
