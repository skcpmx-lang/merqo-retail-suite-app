# MERQO v1.1.4 — Windows build & publication runbook (unsigned installers)

Audience: whoever operates the Windows x64 build host (or the GitHub Actions runner) for the
v1.1.4 production release.

**Code signing is no longer a prerequisite.** The owner has accepted **unsigned** installers for
v1.1.4. No certificate is purchased or provisioned, no signing secret is stored, and an unsigned
build is **never reported as a failure**. Everything that used to block on Authenticode has been
removed from the packaging scripts, the release workflow, the verification tool and the tests.

Status of this document: **runbook — the Windows build itself has not been executed.** This Linux
sandbox cannot produce Windows installers (no Windows host, no NSIS, `node-gyp` cannot cross-compile
`better-sqlite3`). Nothing below claims a size, hash or timestamp that does not exist yet.

## 2. Build host provisioning (Route B)

**Required:** Windows 10 21H2+ / Windows 11, **x64** (not ARM, not WSL), ≥ 8 GB RAM, ≥ 5 GB free
disk on the build volume, network access to the npm registry and Electron/NSIS mirrors.

1. Node.js 22 LTS (x64), `npm i -g npm@10`.
2. **Visual Studio 2022 Build Tools** with “Desktop development with C++” + Windows 10/11 SDK —
   needed to compile `better-sqlite3` for Electron's ABI.
3. Python 3.11 x64 on `PATH` (node-gyp).
4. Git for Windows, GitHub CLI (`gh auth login`).

```bat
git clone https://github.com/skcpmx-lang/merqo-retail-suite-app.git
cd merqo-retail-suite-app
git checkout v1.1.4
git rev-parse HEAD > build-commit.txt
npm ci
```

Nightly/weekly builds: `.nightly` is **not** required; the ordinary `npm ci` installs the exact
lockfile.

## 3. Build

```bat
npm run build
npm run dist:app
npm run dist:license-generator
```

Each packaging script first prints its signing mode:

```
[app] signing: unsigned (accepted by owner)
[license-generator] signing: unsigned (accepted by owner)
```

That line is informational. If a certificate happens to be configured (`CSC_LINK` +
`CSC_KEY_PASSWORD`, `WINDOWS_CODE_SIGNING_SUBJECT`, or Azure Trusted Signing) the scripts use it
automatically and the line says so — but **absence of a certificate never aborts the build**.

Expected outputs:

| File | Produced by |
| --- | --- |
| `packages/app/release/Sauda-Retail-Suite-Setup-1.1.4.exe` | `npm run dist:app` |
| `packages/license-generator/release/Sauda-License-Generator-1.1.4.exe` | `npm run dist:license-generator` |

Copy both into `artifacts/` in the repository root; `verify-installer.mjs` and `SHA256SUMS.txt`
assume that directory.

## 4. Verification gates

Gates 1–4 are automated by one command; Gate 5 is manual and recommended. Run them on the build
host, in this order, and keep the console output as evidence.

```bat
node scripts/verify-installer.mjs --dir artifacts
```

Exit code 0 writes `artifacts/SHA256SUMS.txt` from the **final** files. A non-zero exit means no
checksum file is written — fix the cause; never hand-write a hash.

### Gate 1 — version metadata and architecture (hard stop)

`verify-installer.mjs` checks ProductVersion/FileVersion start with `1.1.4`, the PE machine field is
`8664` (x64), and each file is implausibly small to be a real NSIS installer.

Optional manual spot check:

```bat
powershell -NoProfile -Command "(Get-Item 'artifacts\Sauda-Retail-Suite-Setup-1.1.4.exe').VersionInfo | Format-List ProductName,ProductVersion,FileVersion"
powershell -NoProfile -Command "(Get-Item 'artifacts\Sauda-License-Generator-1.1.4.exe').VersionInfo | Format-List ProductName,ProductVersion,FileVersion"
```

Expected `ProductName`: `Sauda Retail Suite` / `Sauda License Generator`.

### Gate 2 — native dependency is a real win32-x64 binary

```bat
dir "packages\app\release\win-unpacked\resources\app.asar.unpacked\node_modules\better-sqlite3\build\Release"
```

`better_sqlite3.node` must start with `4D 5A` (PE) and report machine `8664`. A `.so`/`.dylib`
means the packaging ran on the wrong host.

### Gate 3 — no private licence-signing key material (hard stop)

`verify-installer.mjs` scans the installers and the unpacked tree for Ed25519 private-key markers,
`.pfx`/`.pem`/`.key` files and any `*PRIVATE KEY*` text. The Main App must ship **only** the public
verification key (`packages/core/src/licensing/publicKey.ts`). Any hit ⇒ stop, do not upload.
This check is about Sauda's own licence-signing system, which is unrelated to Windows code signing
and must never be weakened.

### Gate 4 — Authenticode: informational only

```bat
powershell -NoProfile -Command "Get-AuthenticodeSignature 'artifacts\Sauda-Retail-Suite-Setup-1.1.4.exe' | Format-List Status,StatusMessage"
powershell -NoProfile -Command "Get-AuthenticodeSignature 'artifacts\Sauda-License-Generator-1.1.4.exe' | Format-List Status,StatusMessage"
```

Expected: `Status : NotSigned`. `verify-installer.mjs` prints one summary line per file:

```
Authenticode: artifacts/Sauda-Retail-Suite-Setup-1.1.4.exe — Unsigned — accepted by owner.
```

Unsigned is **the accepted outcome**, not a defect. To make signing mandatory again (a future,
owner-approved policy switch) add `--require-signature`, which also requires an RFC-3161 timestamp.

### Gate 5 — clean-machine install smoke (recommended before publishing)

On a Windows 11 x64 VM with no dev tools:

1. Run both installers; confirm the per-user install path, desktop and Start-menu shortcuts
   (Bangla names) and that Defender/SmartScreen shows **“Windows protected your PC”** →
   “More info” → “Run anyway”.
2. Launch the Main App → activation screen → load a licence file issued by the v1.1.4 License
   Generator → activate → restart the app → still activated.
3. Uninstall → confirm the database/backups **survive** (`deleteAppDataOnUninstall: false`).

## 6. Wording rules (do not overstate)

- Never describe an unsigned installer as signed, “trusted” or “verified by Microsoft”.
- Say **“Unsigned — accepted by owner.”** and mention that Windows may show
  “Unknown publisher” / SmartScreen for the first downloads.
- Do not claim SmartScreen reputation. Reputation accrues over downloads and weeks, not by intent.
- Only report test counts you actually observed; the owner's T01–T45 hardware matrix
  (printer, scanner, cash drawer, customer display) is **not** covered by CI and must stay
  `NOT TESTED` until the owner runs it on real hardware.

## 7. Publication (manual, draft first)

```bat
:: 1. Verify the tag points at the commit you built, and that the notes are filled in
git rev-parse v1.1.4
node scripts\check-release-notes.mjs --require-filled

:: 2. Create a DRAFT release with exactly two assets + checksums (nothing public yet)
gh release create v1.1.4 ^
  artifacts\Sauda-Retail-Suite-Setup-1.1.4.exe ^
  artifacts\Sauda-License-Generator-1.1.4.exe ^
  artifacts\SHA256SUMS.txt ^
  --title "Sauda Retail Suite v1.1.4" ^
  --notes-file docs\V1.1.4_RELEASE_NOTES.md ^
  --draft --verify-tag

:: 3. Re-download the uploaded assets into a clean directory
gh release download v1.1.4 --dir verify --pattern "*.exe"
gh release download v1.1.4 --dir verify --pattern "SHA256SUMS.txt"
certutil -hashfile verify\Sauda-Retail-Suite-Setup-1.1.4.exe SHA256
certutil -hashfile verify\Sauda-License-Generator-1.1.4.exe SHA256

:: 4. Publish only if the re-downloaded hashes match SHA256SUMS.txt
gh release edit v1.1.4 --draft=false
```

Rules:

- Exactly **two** `.exe` files plus `SHA256SUMS.txt` — no extra artefacts, no debug symbols.
- Do **not** touch the published `v1.1.3` release or its assets.
- If a hash differs, delete the draft, rebuild, and repeat. Never edit `SHA256SUMS.txt` by hand.

## 8. Rollback of a bad release

```bat
gh release edit v1.1.4 --draft=true      :: hide it again (keeps assets for inspection)
gh release delete-asset v1.1.4 <name>    :: remove a specific bad asset
```

Deleting the tag (`git push --delete origin v1.1.4`) is a last resort; v1.1.3 stays downloadable
throughout, so customers are never left without a release.

---

## 9. Key-handling rules (non-negotiable)

1. The **licence-signing private key** belongs to the License Generator only. It must never appear
   in the Main App, an installer, this repository, CI variables, logs or chat.
2. The Main App ships only public verification material (`publicKeyB64` + `KEY_ID`).
3. If a licence file or key is ever exposed, rotate the keypair, publish a new public key in an app
   update and re-issue licences; there is no remote kill switch for already-shipped builds.
4. Windows code signing has no key material at all under the new policy — nothing to leak.

## 11. One-page execution order

1. `git checkout v1.1.4` → record `git rev-parse HEAD`.
2. `npm ci && npm run build`.
3. `npm run dist:app && npm run dist:license-generator`.
4. Copy the two `.exe` files into `artifacts/`.
5. `node scripts/verify-installer.mjs --dir artifacts` → exit 0, `SHA256SUMS.txt` created.
6. Clean-VM install smoke (§4 Gate 5).
7. Fill the evidence block (§5) from the real output.
8. `gh release create … --draft` → re-download → compare hashes → `--draft=false`.
