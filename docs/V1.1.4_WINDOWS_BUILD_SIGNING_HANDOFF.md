Do **not** set `ELECTRON_SKIP_BINARY_DOWNLOAD` on this host.

## 3. Code-signing certificate — the hard prerequisite

No unsigned release is authorised. You need **one** of these three delivery modes, available only
on the build host (never in the repository, never in chat, never in a log):

| Mode | What you hold | What the build needs |
| --- | --- | --- |
| **PFX file** (OV/EV cert that permits software key storage) | `.pfx` + password | env `CSC_LINK=<path\cert.pfx>` and `CSC_KEY_PASSWORD=<password>` for the packaging step |
| **Hardware token** (SafeNet eToken / YubiKey PIV — CA/B Forum default since 2023) | token + PIN | certificate installed in the Windows cert store; run `electron-builder` with `--config.win.certificateSubjectName="<exact subject CN>"` and enter the PIN when prompted |
| **Cloud signing** (Azure Trusted Signing / DigiCert Software Trust Manager) | account + certificate profile + authorised credential | the provider’s signing plugin/credential on the host; `signtool` is called by the plugin, not directly |

**Certificate requirements:** publicly trusted CA · EKU **Code Signing** (`1.3.6.1.5.5.7.3.3`) ·
subject legal name that users will see (“Unknown publisher” disappears only when this matches the
signed subject) · RSA ≥ 3072 or ECC P-256 · validity covering the release date · RFC-3161
timestamping so signatures survive certificate expiry
(`http://timestamp.digicert.com` or the CA’s equivalent).

**Never on the build host:** the licence-signing private key. It is used only by the
licence-issuing step (the License Generator, with a key file the operator selects), never by
`npm run dist:*`, never by Authenticode signing. §11 lists the handling rules.

## 5. Mandatory verification gates (in this order, all must pass)

Gates 1–5 below are automated by `node scripts/verify-installer.mjs --dir artifacts`, which is
what the release job runs. The manual commands are kept as spot checks and as evidence for the
report — run them on the same host, in the same order.

### Gate 1 — Authenticode signature (hard stop)

```bat
powershell -NoProfile -Command "Get-AuthenticodeSignature 'packages\app\release\Sauda-Retail-Suite-Setup-1.1.4.exe' | Format-List Status,StatusMessage,SignerCertificate,TimeStamperCertificate"
powershell -NoProfile -Command "Get-AuthenticodeSignature 'packages\license-generator\release\Sauda-License-Generator-1.1.4.exe' | Format-List Status,StatusMessage,SignerCertificate,TimeStamperCertificate"
```

Required: `Status : Valid` for **both**, `SignerCertificate.Subject` = your organisation,
`TimeStamperCertificate` present. `NotSigned`, `UnknownError`, `HashMismatch` or
`NotTrusted` ⇒ **stop, do not upload**.

Equivalent double-check (optional):

```bat
signtool verify /pa /all /v "packages\app\release\Sauda-Retail-Suite-Setup-1.1.4.exe"
```

### Gate 2 — version metadata and architecture

```bat
powershell -NoProfile -Command "(Get-Item 'packages\app\release\Sauda-Retail-Suite-Setup-1.1.4.exe').VersionInfo | Format-List ProductName,ProductVersion,FileVersion,CompanyName"
powershell -NoProfile -Command "(Get-Item 'packages\license-generator\release\Sauda-License-Generator-1.1.4.exe').VersionInfo | Format-List ProductName,ProductVersion,FileVersion"
```

Expected: `ProductVersion` and `FileVersion` start with `1.1.4`, `ProductName` =
`Sauda Retail Suite` / `Sauda License Generator`.

### Gate 3 — native dependency is a real win32-x64 binary

```bat
dir "packages\app\release\win-unpacked\resources\app.asar.unpacked\node_modules\better-sqlite3\build\Release"
powershell -NoProfile -Command "$b=[IO.File]::ReadAllBytes('packages\app\release\win-unpacked\resources\app.asar.unpacked\node_modules\better-sqlite3\build\Release\better_sqlite3.node'); '{0:X2}{1:X2}' -f $b[0],$b[1]"
```

Expected: `better_sqlite3.node` exists, header `4D5A` (**MZ** = PE). `7F454C46` (ELF) means a
Linux binary was packaged — the installer must be rebuilt on Windows.

```bat
:: x64, not arm64/i386
powershell -NoProfile -Command "$p='packages\app\release\win-unpacked\Sauda Retail Suite.exe'; $fs=[IO.File]::OpenRead($p); $br=New-Object IO.BinaryReader($fs); $fs.Position=0x3C; $off=$br.ReadInt32(); $fs.Position=$off+4; '{0:X4}' -f $br.ReadUInt16()"
:: expected 8664
```

### Gate 4 — no private licence-signing key material

```bat
node scripts\verify-installer.mjs --dir artifacts
```

This script (already in the repo) rejects installers under 20 MB, scans the `.exe` bytes and the
`win-unpacked\resources` for PEM headers, `PRIVATE KEY-----`, Ed25519 PKCS#8 headers and a
`sauda-private` marker, and then writes `SHA256SUMS.txt` **from the final files**.

Also inspect the packaged app explicitly:

```bat
npx --yes @electron/asar list "packages\app\release\win-unpacked\resources\app.asar" | findstr /i "pem key p12 pfx license"
:: expected: no key/certificate files; only normal source files
:: (same for packages\license-generator\release\win-unpacked\resources\app.asar)
```

Exit code must be 0. Any hit ⇒ stop.

### Gate 5 — hashes from the final signed files

```bat
mkdir artifacts 2>nul
copy "packages\app\release\Sauda-Retail-Suite-Setup-1.1.4.exe" artifacts\
copy "packages\license-generator\release\Sauda-License-Generator-1.1.4.exe" artifacts\
node scripts\verify-installer.mjs --dir artifacts
certutil -hashfile "artifacts\Sauda-Retail-Suite-Setup-1.1.4.exe" SHA256
certutil -hashfile "artifacts\Sauda-License-Generator-1.1.4.exe" SHA256
```

`artifacts\SHA256SUMS.txt` must contain exactly two lines, lowercase hex, two spaces, file name:

```
<64 hex>  Sauda-Retail-Suite-Setup-1.1.4.exe
<64 hex>  Sauda-License-Generator-1.1.4.exe
```

Hashes are computed **after** signing — signing changes the bytes, so a hash taken before signing
is invalid. Never paste a hash you did not compute from a file you have.

## 10. Release-pipeline defects found — reported, NOT fixed

Per instruction, no merged production source was modified. These are release-process gaps, not
application defects; the app code is untouched.

**Status: D-1, D-2 and D-3 are RESOLVED** by the release-hardening change on top of `88db3a5`
(`scripts/lib/{signing,installer-checks,release-notes}.mjs`, `scripts/check-signing-env.mjs`,
`scripts/check-release-notes.mjs`, the rewritten `scripts/verify-installer.mjs`, the packaging
scripts, `.github/workflows/release.yml`, and 42 tests under `scripts/tests/`). D-4, D-5, C-1 and
O-1 remain and are unchanged.

**D-1 (high) — unsigned builds can be published automatically.** *(resolved: workflow is manual-
dispatch only with `contents: read` and no release action; packaging scripts refuse to run without
a signing method; `verify-installer.mjs` refuses anything not `Status: Valid`.)* `.github/workflows/release.yml`
has no signing credentials and no signature check, and its publish step runs on any `v*` tag push
with `draft: false`. `win.forceCodeSigning` is not set in either `build` config, so
`electron-builder` silently produces an unsigned installer. Proposed minimal fix (needs approval):
pass `CSC_LINK`/`CSC_KEY_PASSWORD` (or the chosen cloud-signing variables) into both packaging
steps, add `"forceCodeSigning": true` under `build.win` in `packages/app/package.json` and
`packages/license-generator/package.json`, and make the job fail when
`Get-AuthenticodeSignature` is not `Valid`.

**D-2 (medium) — post-package verification does not check signatures or metadata.**
*(resolved: the gate now checks Authenticode `Status: Valid` + timestamp, ProductVersion and
FileVersion against the release version, PE machine `8664`, both expected artefact names, size,
key material, and only then writes `SHA256SUMS.txt`.)*
`scripts/verify-installer.mjs` checks size, forbidden key material and writes `SHA256SUMS.txt`,
but never inspects Authenticode, `VersionInfo`, or the PE machine type. Proposed: add those three
checks (PowerShell or `signtool verify`), or add a companion `scripts/verify-signed-release.ps1`
invoked by the workflow and by hand.

**D-3 (medium) — CI-generated release notes would omit the mandatory disclosures.**
*(resolved: the workflow no longer generates notes; it requires
`docs/V1.1.4_RELEASE_NOTES.md`, checks the mandatory sections and disclosures, and with
`--require-filled` refuses to pass while any `<placeholder>` remains.)* The workflow
publishes with `generate_release_notes: true`, which produces a commit list, not the required
verification-status sections. Proposed: publish with `body_path: docs/V1.1.4_RELEASE_NOTES.md`.

**D-4 (low) — the “Stamp version” input can detach artefacts from the commit.** A
`workflow_dispatch` run with `version` rewrites manifests in the runner without a commit, so the
built installer would not correspond to any commit on `main`. Since 1.1.4 is already stamped in
source, leave that input empty.

**D-5 (low, not a defect but an unverified path) — `ELECTRON_SKIP_BINARY_DOWNLOAD: '1'` is set
for `npm ci` on the Windows runner.** It worked for v1.1.3 (the published installers are real), so
the path is proven by history, but it was not re-exercised in this cycle.

**C-1 (caveat, not a defect) — `npm run verify` was last exercised on Linux CI.** It is plain
Node (`scripts/verify.mjs` spawns `process.execPath`), so it is expected to run unchanged on
Windows; a platform-specific failure (path separator, shell assumption) is a harness issue to
report, not evidence of an application defect.

**O-1 (observation) — `packages/license-generator` declares `better-sqlite3` 13.0.3** even though
its build appears to need only the licensing code. This inflates the generator installer and
means it too must be built on Windows x64. Not changed; worth a separate look after the release.

Apply D-1/D-2/D-3 only with explicit authorisation, as a reviewed change on top of `88db3a5` —
not silently during packaging.

## 11. Key-handling rules (non-negotiable)

1. The **licence-signing private key** is used only by the licence-issuing step. It must never be
   on the build host, in the repository, in CI secrets used for building, in the installers, in a
   chat message or in a log.
2. The **Authenticode key** is separate from the licence-signing key. Signing mode PFX/token/cloud
   applies to the installers only.
3. Secrets are supplied as environment variables or a token PIN prompt on the build machine. They
   are never written into `packages/*`, `.github/workflows/*`, a script, or a shell history that
   is shared.
4. `npm run verify` includes a secrets scan and `scripts/package-license-generator.mjs` refuses to
   package if key material is found in tracked sources. Both must pass in the release run.
5. If a key is ever suspected exposed: stop the release, rotate the licence-signing key with
   `scripts/generate-signing-keys.mjs` and re-issue licences, and re-run the Authenticode
   certificate issuance. Report it before publishing anything.
6. Build logs and CI logs may be attached as evidence, but must be re-read for accidental secret
   echo before upload.
