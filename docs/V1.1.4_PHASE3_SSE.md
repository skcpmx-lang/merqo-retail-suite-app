# v1.1.4 · Phase 3 · SSE route — wiring and hardening

Scope of this pass: integrate the authenticated event stream into `/api/v1` properly, bound its
resources, and prove the failure modes. **Renderer migration and complete Client Mode are still not
done** and are not claimed here.

## 1. Route contract

```
GET /api/v1/events
  x-sauda-device, x-sauda-ts, x-sauda-nonce, x-sauda-sign   Ed25519 request signature (mandatory)
  x-sauda-session: <token>            or  ?session=<token>
  Last-Event-ID: <seq>                or  ?last_event_id=<seq>     (absent = live only)
→ 200 text/event-stream
      x-sauda-retention-floor: <n>
      retry: 2000
      id: <outbox seq>
      event: <type> | resync | closed
      data: {…}  |  {"reason":"HISTORY_TRUNCATED","from":n}  |  {"reason":"revoked"}
  400 BAD_LAST_EVENT_ID     malformed resume id
  401 MISSING_SIGNATURE / AUTH_REQUIRED / SESSION_REVOKED
  403 SESSION_DEVICE_MISMATCH / DEVICE_PENDING / DEVICE_REVOKED
  429 STREAM_LIMIT          concurrent-stream policy reached
```

Authentication is the same code path as every other `/api/v1` route: signature → approved device →
session bound to that device → store filter from the device row. There is no stream token.

## 2. What changed in this pass

| Area | Before | Now |
|---|---|---|
| Registry | `Map<deviceId, stream>` inside `api.ts` | `EventStreamHub` (`net/sse.ts`), testable on its own, one stream per device |
| Concurrent streams | unbounded | `sseMaxStreams` (default **32**), `429 STREAM_LIMIT` before opening |
| Slow clients | unbounded `res.write` | connection closed as `slow-consumer` past `sseMaxBufferedBytes` (default **1 MiB**), resumes on `drain` |
| Resume id | lenient `Number()` | strict `^\d{1,15}$`; otherwise `400 BAD_LAST_EVENT_ID` |
| Truncated history | silent gap | `event: resync` `{reason: HISTORY_TRUNCATED, from: floor}` + `x-sauda-retention-floor` |
| Close reasons | one generic reason | `revoked`, `session-expired`, `device-not-approved`, `server-stop`, `slow-consumer`, `replaced`, `client-closed`, `error` |
| Retention | delivered-only prune | `pruneEventsByAge` (age window **and** minimum count), floor recorded in `meta` |
| Logging | reason + last id | adds `device_id`, `store_id`, `resume_from`, `truncated`, stream count — never tokens/nonces/signatures |

## 3. Test evidence (26 SSE tests: 12 previous + 14 new)

Negative first, all over a real TLS listener with a real SQLite outbox:

* **Authorisation** — unsigned stream `MISSING_SIGNATURE` · no session `AUTH_REQUIRED` · another
  device's session `SESSION_DEVICE_MISMATCH` · already-expired session at connect `AUTH_REQUIRED` ·
  revoked session at connect `AUTH_REQUIRED` · pending device `DEVICE_PENDING` · revoked device
  `DEVICE_REVOKED`; every one leaves `streamCount() === 0`.
* **Live lifecycle** — session expiring mid-stream closes it with `session-expired`; session revoked
  mid-stream closes it; revoking the device closes it with `revoked`; server stop closes all streams;
  a client disconnect removes its registration.
* **Resume** — `Last-Event-ID` delivers exactly the missed events with no duplicates · a resume point
  beyond the newest event waits and then delivers strictly above it · five malformed ids give
  `400 BAD_LAST_EVENT_ID` · truncated history gives `resync` with the recorded floor and continues at
  `floor + 1` · ids on one stream are unique and ascending.
* **Isolation** — another store's event is never delivered (payload and count asserted).
* **Bounds** — the third stream on a `maxStreams: 2` server gets `429 STREAM_LIMIT` and the count stays
  2 · reconnecting replaces the old stream (`replaced`) and the count stays 1 · a paused socket with
  250 × 4 KiB events is closed as `slow-consumer` (asserted from the logs).
* **Retention** — `pruneEventsByAge` keeps the newest N events, records the floor, never moves it
  backwards, and deletes nothing inside the age window.

## 5. Remaining limitations (honest)

1. **Delivery is polled** (default 1 s), not pushed. Latency is bounded and documented; there is no
   in-process notification from the writer yet.
2. **Store-level filtering only.** Per-role/permission event filtering (a POS device not receiving
   accounting or cost events) is not implemented; actions on event data still go through
   `/api/v1/rpc`, where permissions are enforced.
3. **Retention is not scheduled.** `pruneEventsByAge` exists and is tested, but nothing calls it on a
   timer yet; until then the outbox grows with the shop's event rate.
4. **The renderer does not consume the stream**, and terminal mode is still not migrated
   (`docs/V1.1.4_PHASE3_MILESTONE_D.md` §2). The SSE route working does not make Client Mode complete.
5. **Stream limit is per server process.** There is one process per store, so this is the store's
   limit; it is not coordinated across processes (multi-process serving is not supported).
6. **No per-device rate limit** on reconnect churn beyond the one-stream-per-device rule and the
   global limit.

## 6. Manual Windows two-PC verification

1. Start the Main Server on PC-A (Settings → Network), issue a pairing code, pair and approve PC-B.
2. On PC-B, sign in. Create a sale on PC-A. **Expect:** the event arrives on PC-B within ~1 s and the
   sale appears after refresh.
3. **Resume:** pull PC-B's network cable, make 3 sales on PC-A, reconnect. **Expect:** exactly 3
   events arrive, none twice, with ascending ids.
4. **Restart:** stop the Main Server from the tray and start it again while PC-B stays open. **Expect:**
   the stream reconnects by itself and no event is lost.
5. **Revocation:** revoke PC-B on PC-A. **Expect:** PC-B's stream closes immediately and the UI says
   the device was revoked; a manual retry is refused.
6. **Session expiry:** set a short session TTL (dev build) and wait. **Expect:** the stream closes with
   `session-expired` and PC-B is asked to sign in again.
7. **Truncated history:** after retention has pruned events (dev build, or lower the window), resume
   from an old id. **Expect:** `resync` with `HISTORY_TRUNCATED`, then a full refresh — not a silent
   gap.
8. **Slow client:** suspend PC-B's process for 2 minutes while sales continue on PC-A, then resume.
   **Expect:** PC-B either receives the backlog or is reconnected after `slow-consumer`; the Main PC's
   memory must stay flat.
9. **Load:** connect 3 devices. **Expect:** all three stream; the 33rd connection on the same server
   (dev build with a lower limit) answers `STREAM_LIMIT`, not a hang.
10. **Logs:** in the Main PC's log, confirm stream open/close lines show device id, store id, last
    sequence and reason — and no tokens, nonces, signatures or keys.
