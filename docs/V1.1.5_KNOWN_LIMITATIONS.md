# V1.1.5 — known limitations

Limitations are listed with their **user-visible effect** and what to do about it. Anything that
could be fixed cheaply was fixed and is in the release notes instead; this file is what remains after
that.

## 1. By design (will not be changed)

| Limitation | Effect for the shop | Workaround |
| --- | --- | --- |
| The Main PC owns the only database | A Client PC cannot trade while the Main PC is off or unreachable | keep the Main PC on during trading hours; the tray keeps the server alive when the POS window is closed |
| No offline completed sale on a Client PC | If the network drops mid-sale, the sale cannot be completed there | the cart draft survives; complete the sale when the link returns, or use the Main PC |
| The database is never shared over SMB | You cannot point two PCs at one `.db` file | use Server Mode + pairing; that is the supported multi-PC design |
| New devices need admin approval | A newly paired PC cannot trade until approved on the Main PC | approve in Settings → Devices |
| Licence revocation is offline | A revoked licence keeps working until its expiry date on an already-activated PC | revoke at issue time; plan renewals before expiry |
| Unsigned installers | Windows shows "Unknown publisher" and SmartScreen may warn on first run | verify the SHA-256 against `SHA256SUMS.txt`, then run |

## 2. Operational limitations of this release

| Limitation | Effect | Mitigation |
| --- | --- | --- |
| **No accounting period lock** (A-08) | Nothing prevents back-dating an entry into a month you have already reported; the only guard is the operator | back up before adjusting; do not re-date entries after closing a month; the audit trail records who posted what and when |
| Revocation does not reach an activated PC | As above — it is a licensing-policy decision, not a bug | treat expiry as the enforcement point |
| No multi-currency | Prices are in BDT (integer poisa) | one currency per shop |
| Single-store identity per database | One database belongs to one store | a second branch needs its own Main PC and its own licence |
| Backup retention is manual by default | Old backups accumulate under `%APPDATA%\Sauda Retail Suite\backups` | automatic backups prune old `auto` files; check the folder occasionally |
| No remote/cloud sync | Everything stays on your hardware | keep the off-machine copy discipline (see the user guide) |

## 3. Verification limits of this release

These are limits of *what was tested*, stated so nobody reads more into the release than it earned.
The owner has **deferred** Windows VM testing and physical-hardware testing for v1.1.5 and authorized the
release without them; every row below is therefore recorded as **NOT TESTED — OWNER TESTING DEFERRED**, never as passed:

| Not covered | Consequence | Status |
| --- | --- | --- |
| Interactive Windows desktop run | window management, DPI scaling, Bengali font fallback and tray behaviour are unverified on real Windows | **NOT TESTED — OWNER TESTING DEFERRED** — see `V1.1.5_VM_TEST_PLAN.md` |
| Two-PC LAN on real hardware | pairing, approval, revocation propagation and sleep/wake are covered only against loopback sockets | **NOT TESTED — OWNER TESTING DEFERRED** |
| Printer / scanner / cash drawer | receipt layout and drawer kick are unverified on hardware | **NOT TESTED — OWNER TESTING DEFERRED** |
| Real v1.1.4 shop upgrade | migrations are tested against synthetic databases | **NOT TESTED — OWNER TESTING DEFERRED** (T34/T35) |
| Antivirus interference | the A-14 fix is designed for it, but no scanner was active during testing | **NOT TESTED — OWNER TESTING DEFERRED** (T36) |
| Performance on customer hardware | no throughput figures are published because none were measured on a customer machine | not claimed |

## 4. Things that were deliberately not done in a patch release

| Not done | Why |
| --- | --- |
| Accounting period lock (A-08) | it changes posting rules and the UI; a patch release must not change how the books behave under the owner's feet |
| Merging the two money formatters (A-09) | display-only refactor across 35 screens at release time is risk without user benefit; a divergence check is scheduled |
| Dark mode | the product is a single light theme by design; a half-done dark mode is worse than none |
| Removing every `any` in the codebase | 279 annotations, mostly in query row types; doing it in a patch release would out-size the actual fixes and make review impossible |
