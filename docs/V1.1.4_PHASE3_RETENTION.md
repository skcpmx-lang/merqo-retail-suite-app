# v1.1.4 Phase 3 — Event retention policy

The outbox (`event_outbox`) exists to tell other devices *what changed*. It is not a
business record: sales, payments, stock and accounting live in their own tables and are
never touched by retention.

## Policy

| Rule | Value | Why |
| --- | --- | --- |
| Age window | 7 days (`olderThanMs`) | A terminal that was off over a weekend still finds its backlog. |
| Minimum kept | newest 5 000 events (`keepLatest`) | Small shops keep a full week of *activity*, not just two hours. |
| Deletion order | oldest first, only below `latest - keepLatest` | Never removes an event a client can still legitimately resume from. |
| Floor | highest deleted sequence → `meta.event_retention_floor` | Monotonic; never moves backwards. |
| Resume below floor | `event: resync {reason:'HISTORY_TRUNCATED', from}` | The client refetches state instead of silently missing changes. |
| Schedule | at startup, then hourly | Bounded work, no unbounded outbox growth. |

## Safety

- The delete runs in one `db.transaction()`; readers never observe a half-pruned outbox.
- If the connection already has an open transaction (a business write in flight) the tick
  is **skipped**, never nested.
- `busy_timeout` is set to 2 s so a concurrent writer delays the prune instead of failing it.
- Any error is logged (`event retention tick failed`) and the timer continues; a closed or
  corrupt database cannot crash the app from the timer.
- `pruneEventsByAge` only deletes rows that are **both** older than the window **and** below
  the newest `keepLatest` ids, so a mis-set clock cannot erase the tail.

## Tunables

```ts
startEventRetention(db, {
  intervalMs: 60 * 60 * 1000,      // hourly
  olderThanMs: 7 * 24 * 60 * 60 * 1000,
  keepLatest: 5000,
  log: (level, message, detail) => {},
});
```

`runOnce()` is exposed for the tray/manual maintenance and for tests.
