## 3. Installer verification rules (what "verified" means)

`scripts/verify-installer.mjs` refuses to write checksums — and therefore refuses to let anything be
published — unless, for both files:

| Check | Rule |
| --- | --- |
| Presence | both expected artefact names exist and are ≥ 20 MB |
| Version metadata | `ProductVersion` and `FileVersion` both match `1.1.4` (read with PowerShell) |
| Architecture (payload) | every packaged application executable is a PE image with machine `8664`; the Windows x64 native module (`prebuilds/win32-x64.node` or `build/Release/*.node`) is present and `8664` |
| Architecture (bootstrap) | the NSIS installer stub may be `014C` (32-bit by design) — reported, not failed; an `AA64` (arm64) installer is refused |
| Native dependency | a native `.node` module must be present in the payload; missing means SQLite would be missing at runtime |
| Key material | installer bytes **and** unpacked resources are scanned for a PEM private key block, an OpenSSH private key block, the Ed25519 PKCS#8 DER prefix and the generator's private marker |
| Authenticode | status is read and reported; unsigned is accepted (policy) and is **not** a failure |
| Integrity | SHA-256 computed from these exact files and written to `SHA256SUMS.txt` |

## 5. Defects found by the release pipeline, and how they were fixed

The Windows gate caught three real problems that the Linux-only CI of the previous cycle could not
see. Each was fixed in code with regression tests; none was bypassed, skipped or silenced.

| Run | Failure | Root cause | Fix |
| --- | --- | --- | --- |
| `41884623649` | `tests: core` → `EBUSY: resource busy or locked, unlink '…\shop.db'` | thirteen suites deleted their temp directory while a SQLite connection was still open; Linux allows unlinking an open file, Windows does not | databases are opened through a tracked helper and closed before removal; temp removal retries briefly for Windows handle lag but still throws on a leak; `openDatabaseCount()` plus a per-file leak guard make this class of bug fail on **Linux** too; regression tests cover lock release, idempotent close, and a failed open of a newer-schema database |
| `41901113618` | `architecture is 014C (expected 8664)` for both installers; `packaged resource app.asar contains: PEM header` | an NSIS installer is a 32-bit bootstrap even when it installs a 64-bit app; and key-free shipped code legitimately contains the literal `-----BEGIN` (the app generates its own TLS certificate PEM, the Settings screen has a certificate paste field, the generator strips PEM armour from a key the owner supplies) | the x64 requirement moved to the payload (`evaluatePayload`: app executables and the Windows x64 native module must be `8664`), the i386 bootstrap is reported instead of failed; the key scan now looks for actual private-key material (private key block, OpenSSH block, Ed25519 PKCS#8 prefix, `sauda-private`) |
| `41903178433` | `packaged binary …/prebuilds/linux-x64.node is unknown (expected 8664)` | better-sqlite3 ships a prebuild for every platform and `node-gyp-build` loads only the matching one; requiring PE x64 of all of them rejected files never loaded on Windows | `classifyPayloadBinary()` separates app executables and Windows x64 modules (hard requirements) from other-platform prebuilds (reported as a warning, and noted as a future installer-size reduction) |

Commits: `1d1fbe7` (Windows file-lock fix + leak guard), `b6f6386` (payload architecture,
key-material scan), `18f77de` (cross-platform prebuilds, payload classification).

## 6. Publication safety

- The release was created as a **draft** and could only be promoted after the re-download and
  re-verification step passed; every earlier step aborts the job on failure.
- Publication steps are gated on `startsWith(github.ref, 'refs/tags/v')`, so a manual run builds and
  verifies but publishes nothing.
- An already-published release is never overwritten: the workflow inspects `isDraft` and refuses.
- The asset list on the draft must be exactly the three expected files.
- No `secrets.*` is referenced anywhere in the release workflow; Authenticode is optional and no
  certificate, PFX, token or timestamp service exists in the pipeline.

## 7. Preserved and untouched

- **v1.1.3** release and tag are untouched; its assets were not modified or deleted.
- No destructive migration was added: v1.1.4 upgrades the v1.1.3 database in place (new tables only)
  and writes a pre-upgrade copy; the rollback path is documented in the release notes.
- The licence-signing private key is not in the app, the installers, git or CI, and the app keeps only
  public verification material. The v1.1.4 payload was scanned for key material as part of the gate.
